# LynJS 프로젝트 배경 및 개발 방향

## 1. 문서 목적

본 문서는 LynJS 프로젝트의 개발 배경, 문제 정의, 핵심 목표, 기술적 기반, 설계 원칙 및 초기 개발 범위를 정의한다.

LynJS의 목적은 JSX Compiler나 DOM Binding Engine을 처음부터 새로 구현하는 것이 아니다.

이미 검증된 `dom-expressions`를 JSX 및 Fine-grained DOM Rendering 기반으로 활용하고, 그 위에 LynJS 고유의 다음 영역을 설계하는 것을 핵심 범위로 한다.

- Object-Oriented Component Model
- Custom Elements 기반 Component Lifecycle
- Decorator 중심 API
- Reactive Property Model
- Component와 Reactive Scope의 통합
- Framework Runtime 및 Developer Experience

세부적인 Runtime 구조와 Decorator 구현 방식은 별도의 Architecture 문서에서 정의한다.

---

# 2. 프로젝트 개요

**LynJS**는 Custom Elements를 기반으로 하는 객체지향 프론트엔드 프레임워크다.

LynJS는 웹 플랫폼의 객체 모델을 Component System의 기반으로 사용하고, `dom-expressions`를 JSX 및 Fine-grained DOM Binding 계층으로 활용한다.

프로젝트의 핵심 구성은 다음과 같다.

```text
LynJS
 │
 ├─ Object-Oriented Component Model
 │
 ├─ Decorator API
 │    ├─ @element
 │    ├─ @state
 │    └─ @property
 │
 ├─ Reactive Property Runtime
 │
 ├─ Custom Element Lifecycle Integration
 │
 └─ Rendering Layer
      │
      └─ dom-expressions
           ├─ JSX Transform
           ├─ DOM Creation
           └─ Fine-grained DOM Binding
```

LynJS가 목표로 하는 기본적인 Component API는 다음과 같다.

```tsx
import { LynElement, element, state } from 'lynjs';

@element('lyn-counter')
class Counter extends LynElement {
  @state()
  count = 0;

  render() {
    return <button onClick={() => this.count++}>Count: {this.count}</button>;
  }
}
```

이 코드에서 LynJS가 직접 정의하는 주요 영역은 다음과 같다.

```text
LynElement
    └─ Component Object / Lifecycle

@element
    └─ Custom Element Registration

@state
    └─ Reactive Property

Component Scope
    └─ Reactive Resource Ownership

JSX / DOM Binding
    └─ dom-expressions
```

# 3. 문제 정의

현재 프론트엔드 생태계에는 선언적 UI, Fine-grained Reactivity, Web Components 등 각각의 문제를 해결하는 성숙한 기술들이 존재한다.

LynJS는 이 기능들을 모두 새로 구현하는 것을 목표로 하지 않는다.

프로젝트가 해결하려는 핵심 문제는 다음과 같다.

> **기존 Fine-grained DOM Rendering 기술을 활용하면서, Custom Elements를 중심으로 한 객체지향 Component Model과 Reactive Property 기반의 개발 경험을
> 제공할 수 있는가?**

이를 위해 LynJS는 기술적 문제를 두 영역으로 분리한다.

### 재사용할 영역

이미 검증된 구현을 적극적으로 활용한다.

```text
JSX Transform
DOM Creation
Fine-grained DOM Binding
Dynamic DOM Update
```

이 영역에는 `dom-expressions`를 활용한다.

### LynJS가 설계할 영역

LynJS의 정체성과 직접 연결되는 부분은 자체적으로 정의한다.

```text
Object-Oriented Component Model
Decorator Semantics
Reactive Property
Custom Element Lifecycle
Reactive Scope Ownership
Property / Attribute Model
Component API
Framework DX
```

# 4. 기술적 기반: dom-expressions

LynJS의 Rendering Layer는 `dom-expressions`를 기반으로 한다.

`dom-expressions`는 JSX 표현을 실제 DOM 생성 코드와 Fine-grained Reactive Binding으로 연결하기 위한 기반을 제공한다.

따라서 LynJS에서는 다음 영역을 처음부터 별도로 구현하지 않는다.

- JSX AST 기반 DOM Compiler
- 기본 DOM 생성 Helper
- Reactive Text Binding
- Dynamic Child 처리
- Fine-grained DOM 업데이트 알고리즘
- JSX Event Binding의 기본 구조

LynJS는 이 계층을 활용하여 Component Model과 Reactivity Integration에 집중한다.

전체 구조는 다음과 같다.

```text
             LynJS Application

@element
class Counter extends LynElement
          │
          ├──── @state
          │       │
          │       ▼
          │  Reactive Property
          │       │
          │       ▼
          │  LynJS Reactivity
          │
          └──── render()
                  │
                  ▼
                 JSX
                  │
                  ▼
           dom-expressions
                  │
          ┌───────┴────────┐
          │                │
      DOM Creation   Reactive Binding
          │                │
          └───────┬────────┘
                  ▼
                 DOM
```

이 구조를 통해 LynJS는 Rendering Engine 자체보다 Component Architecture에 개발 자원을 집중할 수 있다.

# 5. 프로젝트 목표

## 5.1 객체지향 Component Model

LynJS에서 Component는 함수 호출이 아니라 실제 객체다.

```tsx
@element('user-card')
class UserCard extends LynElement {
  @state()
  expanded = false;

  toggle() {
    this.expanded = !this.expanded;
  }

  render() {
    // ...
  }
}
```

Component는 다음 요소를 가진다.

```text
Component Object
 ├─ Identity
 ├─ State
 ├─ Properties
 ├─ Methods
 ├─ Lifecycle
 └─ View
```

이 구조는 Custom Elements의 객체 모델과 직접 연결한다.

# 6. Custom Elements를 Component 기반으로 사용

LynJS Component는 `HTMLElement` 계열의 실제 Custom Element다.

```text
HTMLElement
    ▲
    │
LynElement
    ▲
    │
Application Component
```

예를 들어,

```tsx
@element('lyn-counter')
class Counter extends LynElement {}
```

는 최종적으로 다음 형태로 사용할 수 있어야 한다.

```html
<lyn-counter></lyn-counter>
```

`@element()`는 Custom Element 등록과 LynJS Component Metadata 구성을 담당한다.

개념적으로는 다음 책임을 갖는다.

```text
@element("lyn-counter")
        │
        ├─ customElements.define(...)
        └─ LynJS Component Metadata
```

Component를 별도의 Framework Component Representation으로 생성한 뒤 Web Component로 변환하지 않는다.

Custom Element 자체가 Component다.

---

# 7. Reactive Property Model

LynJS는 Reactive State를 객체의 Property로 표현한다.

```tsx
@state()
count = 0;
```

사용자는 별도의 Reactive Container를 직접 조작하지 않는다.

```ts
this.count++;
this.count = 10;
console.log(this.count);
```

LynJS Runtime은 해당 Property의 읽기와 쓰기를 Reactivity System과 연결한다.

개념적인 동작은 다음과 같다.

```text
Property Read
     │
     ▼
Dependency Tracking

Property Write
     │
     ▼
Dependency Trigger
```

내부적으로 Signal 또는 Reactive Node와 유사한 구조를 사용할 수 있지만 Public Component API에서는 이를 숨긴다.

따라서 다음 형태를 기본 API로 사용하지 않는다.

```ts
count.value++;
```

대신 일반적인 Property Semantics를 유지한다.

```ts
this.count++;
```

---

# 8. LynJS Reactivity와 dom-expressions 연결

`dom-expressions`를 사용하는 핵심 조건은 LynJS의 Reactive Property System과 DOM Binding Layer를 연결하는 것이다.

예를 들어 다음 표현에서,

```tsx
<span>{this.count}</span>
```

`this.count`가 변경될 경우 `dom-expressions`가 생성한 Dynamic Binding이 해당 변화를 인식할 수 있어야 한다.

전체 흐름은 다음과 같다.

```text
@state()
count
  │
  ▼
LynJS Reactive Node
  │
  ▼
Dependency Tracking
  │
  ▼
dom-expressions Binding
  │
  ▼
DOM Node
```

상태 변경 시에는 다음 흐름을 가진다.

```text
this.count++
     │
     ▼
Reactive Property Setter
     │
     ▼
Dependency Notification
     │
     ▼
Dynamic Binding
     │
     ▼
DOM Update
```

따라서 LynJS의 핵심 기술 과제는 Fine-grained DOM Update Algorithm 자체를 만드는 것이 아니라,

> **LynJS의 객체 기반 Reactive Property Model을 dom-expressions가 사용하는 Reactive Execution Model과 자연스럽게 연결하는 것**이다.

---

# 9. JSX의 역할

LynJS는 JSX를 기본 UI 문법으로 사용한다.

```tsx
render();
{
  return <button onClick={() => this.count++}>Count: {this.count}</button>;
}
```

JSX Transform 및 기본 DOM Binding 생성에는 `dom-expressions`의 Compiler Infrastructure를 활용한다.

따라서 LynJS가 별도의 범용 JSX Compiler를 처음부터 개발하는 것은 초기 프로젝트 범위에 포함하지 않는다.

프로젝트에서는 JSX Compiler 자체보다 LynJS의 Component 및 Reactive Semantics와 JSX Transform의 Integration에 집중한다.

예를 들어 다음과 같은 LynJS 전용 동작이 필요한지 검토한다.

```text
LynElement 인식
Component Property 전달
Decorator Metadata와 Binding 연결
Custom Element Property 처리
Lifecycle Scope 전달
Event 정책
```

필요한 경우 `dom-expressions` 위에 최소한의 LynJS 전용 Transform 또는 Configuration Layer를 추가한다.

---

# 10. Fine-grained DOM Binding

Fine-grained DOM Binding의 핵심 구현은 `dom-expressions`를 활용한다.

LynJS가 별도의 Virtual DOM을 도입하지 않는다는 원칙은 유지한다.

```text
State Change
     ↓
Reactive Dependency
     ↓
Affected Expression
     ↓
DOM Update
```

다음과 같은 전체 Tree 기반 업데이트를 기본 모델로 사용하지 않는다.

```text
State Change
     ↓
Component Re-render
     ↓
Virtual Tree
     ↓
Diff
     ↓
DOM Patch
```

하지만 Binding 생성과 DOM 업데이트 메커니즘을 LynJS 자체에서 다시 구현할 필요는 없다.

LynJS는 해당 역할을 Rendering Infrastructure에 위임하고 Component Reactivity와 Lifecycle을 담당한다.

# 11. Decorator 중심 Component API

Decorator는 LynJS가 직접 설계하는 핵심 영역이다.

초기 API는 다음 세 가지를 중심으로 한다.

```text
@element
@state
@property
```

## `@element`

Custom Element Component를 정의한다.

```tsx
@element('lyn-counter')
class Counter extends LynElement {}
```

주요 책임:

```text
Custom Element Registration
Component Metadata
Runtime Initialization
```

## `@state`

내부 Reactive State를 정의한다.

```tsx
@state()
count = 0;
```

주요 책임:

```text
Property Reactivity
Dependency Tracking
Change Notification
```

## `@property`

외부에서 전달 가능한 Component Property를 정의한다.

```tsx
@property()
label = "Count";
```

주요 책임:

```text
Public Property
Optional Attribute Integration
Reactive Update
```

향후 다음 Decorator를 검토할 수 있다.

```text
@computed
@effect
@attribute
@query
@event
```

단, 초기 API Surface는 최소화한다.

# 12. Component Lifecycle과 Reactive Scope

LynJS가 자체적으로 해결해야 하는 중요한 영역은 Lifecycle이다.

Reactive Binding이 Fine-grained하더라도 Component가 DOM에서 제거된 이후 Subscription 또는 Effect가 남아 있어서는 안 된다.

따라서 Component Lifecycle과 Reactive Scope를 연결한다.

```text
connectedCallback
       │
       ▼
Component Scope Activate
       │
       ▼
render()
       │
       ▼
DOM Binding Activation
```

제거 시에는 다음과 같이 동작해야 한다.

```text
disconnectedCallback
       │
       ▼
Component Scope Dispose
       │
       ├─ Effect Cleanup
       ├─ Subscription Cleanup
       └─ Resource Cleanup
```

이 Lifecycle Ownership Model은 LynJS Runtime의 핵심 책임이다.

```text
│                              │
│ @element / @state / JSX      │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│     LynJS Component Layer    │
│                              │
│ LynElement                   │
│ Decorator Metadata           │
│ Reactive Properties          │
│ Lifecycle                    │
│ Reactive Scope               │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐

│       dom-expressions        │

└──────────────────────────────┘
```

이 경계를 유지함으로써 Rendering Engine과 LynJS 고유 Component Model의 결합도를 관리한다.

# 15. 프로젝트가 직접 구현하지 않는 영역

초기 단계에서 다음 기능은 새로 구현하지 않는다.

```text
General-purpose JSX Compiler
DOM Template Compiler
Virtual DOM
DOM Diff Algorithm
Fine-grained DOM Mutation Engine
Default Dynamic Child Runtime
```

해당 영역은 가능한 한 `dom-expressions`를 활용한다.

단, LynJS의 Component Semantics를 지원하기 위해 필요한 Adapter 또는 최소한의 Extension은 프로젝트 범위에 포함한다.

---

# 16. 기술적 의존성 원칙

`dom-expressions`를 핵심 Rendering Dependency로 사용하더라도 LynJS의 Public API가 직접 해당 라이브러리에 종속되지 않도록 한다.

Application Code에서는 다음만 보여야 한다.

```tsx
import { LynElement, element, state, property } from 'lynjs';
```

다음과 같은 내부 Rendering API는 Application Layer에 노출하지 않는 것을 원칙으로 한다.

```text
insert
spread
template
delegateEvents
createComponent
```

즉 의존성 방향은 다음과 같아야 한다.

```text
Application
    ↓
LynJS Public API
    ↓
LynJS Runtime
    ↓
dom-expressions
```

Application이 직접 `dom-expressions`에 의존하는 구조는 피한다.

이를 통해 향후 Rendering Layer 변경 또는 Wrapper 구현 가능성을 유지한다.

# 17. 기존 기술과의 관계

LynJS는 다음 기술에서 각각 특정 영역을 활용하거나 참고한다.

| 기술            | LynJS에서의 역할                                 |
| --------------- | ------------------------------------------------ |
| Custom Elements | Component Standard                               |
| Decorators      | Component Metadata / Reactive Property           |
| JSX             | View Syntax                                      |
| dom-expressions | JSX 및 Fine-grained DOM Rendering Infrastructure |
| SolidJS         | Fine-grained Rendering Architecture 참고         |
| TypeScript      | Type System 및 개발 언어                         |

`dom-expressions`는 Solid 계열의 렌더링 기반으로 활용되지만 LynJS의 Component Model은 Solid의 함수형 Component Model과 별도로 정의한다.

즉 다음 두 영역을 구분한다.

```text
Rendering Architecture
    → dom-expressions 활용

Programming Model
    → LynJS 자체 설계
```

# 18. 핵심 기술 과제

`dom-expressions` 도입에 따라 프로젝트의 핵심 기술 과제도 변경된다.

## 18.1 Reactive Adapter

가장 먼저 검증해야 할 부분이다.

LynJS의 다음 API가,

```tsx
@state()
count = 0;
```

`dom-expressions`의 Dynamic Binding과 정상적으로 연결되어야 한다.

```tsx
<span>{this.count}</span>
```

이를 위한 Reactive Primitive Contract를 정의해야 한다.

---

## 18.2 Class Context 유지

JSX Expression에서 다음 코드가 자연스럽게 동작해야 한다.

```tsx
{
  this.count;
}
```

또한 Event Handler에서도 객체 Context가 유지되어야 한다.

```tsx
<button onClick={() => this.increment()}>
```

Component Method 및 Property 접근과 Rendering Runtime 간의 경계를 검증해야 한다.

---

## 18.3 Custom Element Component 처리

JSX에서 LynJS Component를 사용할 경우,

```tsx
<UserCard user={this.user} />
```

또는 Custom Element 형태를 사용할 경우,

```tsx
<user-card user={this.user} />
```

Property Assignment와 Attribute Assignment 정책을 정의해야 한다.

---

## 18.4 Lifecycle Ownership

`dom-expressions`에서 생성된 Reactive Binding과 Effect가 어느 Component Scope에 속하는지 관리할 방법이 필요하다.

```text
LynElement
   │
   └─ Reactive Scope
          │
          └─ DOM Bindings
```

Component가 제거될 경우 Scope 전체를 정리할 수 있어야 한다.

---

## 18.5 Decorator Initialization

Class Field 초기화와 Decorator 적용 시점을 고려하여 다음 동작의 정확한 순서를 정의해야 한다.

```tsx
@state()
count = 0;
```

상속과 초기화 순서 역시 검증 대상이다.

# 19. 초기 프로젝트 구조

초기 Monorepo는 자체 구현 영역과 외부 Rendering Layer를 명확하게 구분한다.

```text
lynjs/
├─ packages/
│  ├─ core/
│  │   ├─ LynElement
│  │   ├─ lifecycle
│  │   └─ component runtime
│  │
│  ├─ reactivity/
│  │   ├─ reactive property
│  │   ├─ dependency
│  │   └─ scope
│  │
│  ├─ decorators/
│  │   ├─ element
│  │   ├─ state
│  │   └─ property
│  │
│  ├─ dom/
│  │   └─ dom-expressions integration
│  │
│  └─ vite-plugin/
│
├─ examples/
│  ├─ counter/
│  ├─ todo/
│  └─ components/
│
├─ tests/
└─ docs/
```

# 20. 개발 단계

## Phase 1 — dom-expressions Integration Prototype

가장 먼저 `dom-expressions`가 LynJS가 원하는 Component Model과 결합 가능한지 검증한다.

최소 목표 코드는 다음과 같다.

```tsx
class Test {
  count = reactive(0);

  render() {
    return <span>{this.count}</span>;
  }
}
```

검증 내용:

```text
JSX Transform
Dynamic Expression
Reactive Dependency
DOM Update
```

```tsx

```

목표는 Reactive Primitive가 Component 코드 밖으로 노출되지 않도록 하는 것이다.

# 21. Core Milestone

LynJS의 첫 번째 Core Milestone은 다음 코드를 기준으로 한다.

```tsx
import { LynElement, element, state } from 'lynjs';

@element('lyn-counter')
class Counter extends LynElement {
  @state()
  count = 0;

  render() {
    return <button onClick={() => this.count++}>Count: {this.count}</button>;
  }
}
```

다음 조건을 충족하면 첫 번째 Architecture 검증이 완료된 것으로 본다.

1. `Counter`가 실제 Custom Element로 등록된다.
2. `count`는 일반 JavaScript Property로 동작한다.
3. `@state()`가 해당 Property를 Reactive하게 만든다.
4. JSX는 `dom-expressions` 기반으로 변환된다.
5. `{this.count}`가 Reactive DOM Binding으로 연결된다.
6. `this.count++` 실행 시 해당 DOM 지점만 갱신된다.
7. Virtual DOM을 생성하지 않는다.
8. Component 전체 Re-render를 필요로 하지 않는다.
9. Component 제거 시 Reactive Resource가 정상적으로 정리된다.
10. `<lyn-counter>`를 표준 Custom Element로 사용할 수 있다.

# 22. 설계 원칙

## UI is an Object

Component는 상태, 행동, Identity와 Lifecycle을 가진 객체다.

## Reactivity is a Property

Reactive State는 객체의 Property로 표현한다.

```tsx
@state()
count = 0;
```

## Decorators Describe the Object

Component Metadata와 Reactive Behavior는 Decorator로 선언한다.

## JSX is the View Syntax

JSX는 LynJS의 기본 View 문법이다.

## Reuse Proven Rendering Infrastructure

Fine-grained DOM Rendering과 JSX Transform을 불필요하게 다시 구현하지 않는다.

`dom-expressions`와 같은 검증된 기반을 적극 활용한다.

## LynJS Owns the Component Model

Rendering Infrastructure를 재사용하더라도 Component, Lifecycle, Decorator 및 Public API의 의미는 LynJS가 정의한다.

## Hide Rendering Internals

`dom-expressions`의 내부 API를 LynJS Application API에 직접 노출하지 않는다.

## Lifecycle Owns Reactive Resources

Binding과 Effect는 명확한 Component Scope에 속해야 한다.

## Standards at the Boundary, Freedom Inside

외부 Component Boundary는 Custom Elements와 DOM 표준을 따르고 내부에서는 적절한 Runtime과 Compiler Infrastructure를 활용한다.

## Prove Before Expanding

Core Component Model과 Rendering Integration이 검증되기 전까지 주변 생태계를 확대하지 않는다.

# 23. 프로젝트 핵심 가설

LynJS 프로젝트가 검증해야 할 핵심 가설은 다음과 같다.

### 가설 1

`dom-expressions`를 활용하면서 SolidJS의 Component Model에 종속되지 않은 별도의 객체지향 Component Model을 만들 수 있다.

### 가설 2

Decorator 기반 Reactive Property를 `dom-expressions`의 Fine-grained Rendering Model과 자연스럽게 연결할 수 있다.

### 가설 3

Reactive Primitive를 Application 코드에 직접 노출하지 않고 일반 Property Semantics를 유지할 수 있다.

### 가설 4

Custom Element Lifecycle을 Reactive Scope의 Ownership Boundary로 사용할 수 있다.

### 가설 5

Rendering Layer를 외부 Infrastructure에 위임하면서도 LynJS의 Public API와 Component Architecture를 독립적으로 유지할 수 있다.

### 가설 6

이 구조를 통해 Component는 외부에서 표준 Custom Element로 사용할 수 있다.

초기 개발의 주요 목적은 이 여섯 가지 가설을 검증하는 것이다.

# 24. 프로젝트 비목표

LynJS 초기 프로젝트에서는 다음을 목표로 하지 않는다.

- JSX Compiler를 처음부터 새로 작성
- Fine-grained DOM Rendering Engine을 새로 작성
- Virtual DOM 구현
- SolidJS Runtime 재구현
- SolidJS Component API 호환
- React 호환 Layer 개발
- 초기 단계에서 SSR 전체 구현
- Router 및 Meta Framework 개발

프로젝트의 핵심은 Rendering 기술 자체를 다시 만드는 것이 아니다.

> **검증된 Fine-grained Rendering Infrastructure 위에 Web Standards 기반의 객체지향 Component Programming Model을 구축하는 것**이 LynJS의 핵심
> 범위다.
