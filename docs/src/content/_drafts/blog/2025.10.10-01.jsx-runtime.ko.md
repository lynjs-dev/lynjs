# LynJS JSX 런타임 만들기

이전 글에서는 Babel 프리셋(`babel-preset-lynjs`)을 구성해 `babel-plugin-jsx-dom-expressions`을 사용할 수 있도록 했다.
그러나 이 단계까지는 JSX를 변환할 준비만 된 상태일 뿐이며, Babel은 JSX를 함수 호출 형태로 바꿔줄 뿐 실제로 DOM을
생성하거나 조작하지는 않는다. 변환된 코드가 동작하려면 이러한 함수 호출을 실제로 수행할 **런타임(runtime)** 이 필요하다.

`babel-plugin-jsx-dom-expressions`에는 이미 이를 위한 공식 런타임인
[`dom-expressions`](https://github.com/ryansolid/dom-expressions) 패키지가 존재한다. 다만 LynJS는 Shadow DOM, hostNode,
attribute 반영 정책 등 자체적인 구조와 철학을 가지고 있기 때문에, `dom-expressions` 런타임을 그대로 사용하는 것만으로는
충분하지 않을 수 있다.

그렇기 때문에 `dom-expressions`를 기반으로 하면서도 LynJS의 설계 방향에 맞게 필요한 부분만 선택적으로 오버라이드할 수
있는 **LynJS 전용 런타임 패키지 `@lynjs/dom`** 을 구현한다.

`dom-expressions`을 사용하기 위해서는 **상태 변화에 반응하여 UI를 자동으로 갱신할 수 있는 반응형(Reactive) 코어**가
반드시 필요하다. 이 반응형 시스템은 단순한 상태 관리 수준이 아니라, 데이터 변화가 DOM 업데이트로 자연스럽게 이어지도록
하는 핵심 메커니즘이다. LynJS에서는 이러한 구조를 프레임워크의 철학에 맞게 직접 구현하며, **`@lynjs/reactive`** 패키지가
그 역할을 담당한다. 이 패키지는 LynJS의 렌더링 시스템과 긴밀히 연결되어 JSX 표현식과 상태 변화가 매끄럽게 동작하도록
지원한다.

## dom-expressions를 사용하기 위한 Babel 설정

`dom-expressions`는 내부적으로 **가상 모듈 이름인 `rxcore`** 를 임포트하고 있으며, 이 `rxcore`는 실제로 존재하는
패키지가 아니라 프로젝트가 사용하는 **반응형 코어가 연결될 자리**를 의미한다. LynJS의 경우 이 반응형 코어가 바로
`@lynjs/reactive` 패키지이므로, Babel을 통해 `rxcore`를 `@lynjs/reactive`로 치환해주어야 한다. 이렇게 임포트를 변환하면
`dom-expressions` 내부에서 사용하는 모든 반응형 API 호출이 LynJS의 코어 로직과 연결되어 동일한 반응형 흐름을 공유하게
되며, 별도의 커스텀 런타임을 추가하지 않고도 LynJS의 반응형 시스템을 그대로 활용할 수 있다. 또한 이러한 치환 과정을
Babel 수준에서 처리하면, 런타임 의존성을 최소화하면서 빌드 시점에 불필요한 코드가 제거될 수 있어 전체 번들이
**tree-shakeable**한 구조로 유지된다.

### babel-preset-lynjs에서 rxcore 연결(치환) 설정하기

`dom-expressions`가 `@lynjs/reactive`를 사용 할 수 있도록 하기위해 `babel-preset-lynjs`에는 `rxcore`라는 가상 모듈을
LynJS의 **실제 반응형 코어**로 연결하기 위한 설정을 추가하도록 한다.

이를 위해 Babel 설정에 `babel-plugin-transform-rename-import`를 추가하고, `rxcore`로 선언된 모든 임포트를
`@lynjs/reactive`로 치환하도록 구성한다. 이렇게 하면 `dom-expressions` 내부에서 사용하는 반응형 함수들이 LynJS의 실제
코어 로직과 직접 연결되어 동일한 반응형 흐름을 공유하게 되며, 결과적으로 런타임 전반이 LynJS의 철학에 맞는 일관된 반응형
구조 위에서 동작하게 된다.

```js
// packages/babel-preset-lynjs/index.js
const jsxTransform = require('babel-plugin-jsx-dom-expressions');
const transformTypeScript = require('@babel/plugin-transform-typescript');
const renameImport = require('babel-plugin-transform-rename-import');

module.exports = function (_context, options = {}) {
  // JSX 옵션은 프로젝트 기본값을 두고, 필요 시 프리셋 옵션으로 덮어쓰기
  const jsxOpts = Object.assign(
    {
      moduleName: '@lynjs/dom', // dom-expressions 엔드포인트
      contextToCustomElements: true,
      wrapConditionals: true,
      generate: 'dom',
    },
    options.jsx || {},
  );

    // rxcore replacement target and actual core path (relative path for package/development) are also open as options  const rxOpts = Object.assign(
    {
      original: 'rxcore',
      // 배포 시
      replacement: '@lynjs/reactive',
      // 모노레포 개발 중이라면 이렇게 바꿔도 됨:
      // replacement: require('path').resolve(__dirname, '../../reactive/src/index.js')
    },
    options.rxcore || {},
  );

  return {
    // node_modules는 일반적으로 무시하지만 dom-expressions만은 통과시켜야 rename이 적용됨
    ignore: ['**/node_modules/(?!dom-expressions)'],

    overrides: [
      // .ts
      {
        test: /\.ts$/,
        plugins: [
          [transformTypeScript, { allowDeclareFields: true }],
          // rxcore → @lynjs/reactive 치환 (도메인 전역 적용)
          [renameImport, rxOpts],
        ],
      },

      // .tsx
      {
        test: /\.tsx$/,
        plugins: [
          [transformTypeScript, { isTSX: true, allowDeclareFields: true }],
          [jsxTransform, jsxOpts],
          [renameImport, rxOpts],
        ],
      },

      // .jsx
      {
        test: /\.jsx$/,
        plugins: [
          [jsxTransform, jsxOpts],
          [renameImport, rxOpts],
        ],
      },
    ],
  };
};
```

### 사용 예시

프로젝트 쪽에서는 프리셋만 선언해 주면 된다. 별도로 `rename-import`를 중복 설정할 필요가 없고, 모노레포 개발 중
`@lynjs/reactive`가 아직 퍼블리시 전이라면 `options.rxcore.replacement`로 상대경로를 넘겨 임시로 연결하면 된다.

```jsonc
// .babelrc (또는 babel 옵션)
{
  "presets": [
    [
      "lynjs",
      {
        // 필요 시 JSX 옵션 커스터마이즈
        "jsx": {
          "hydratable": false,
        },
        // 개발 중에는 내부 경로로 코어 연결
        // "rxcore": { "replacement": "../../packages/reactive/src/reactive.ts" }
      },
    ],
  ],
}
```

이렇게 설정해 두면 `dom-expressions`가 내부에서 임포트하는 `rxcore`가 빌드 타임에 자동으로 `@lynjs/reactive`로 치환되어
LynJS의 반응형 코어와 자연스럽게 이어지고, 프리셋 하나만으로 TS/JSX/코어 연결까지 일괄 적용되므로 유지보수와 트리 셰이킹
측면에서도 깔끔하게 정리된다.

## rxcore 에서 구현 해야 할것들

```ts
export function root<T>(fn: (dispose: () => void) => T) => T;
export function effect<T>(fn: (prev?: T) => T, init?: T): void;
export function memo<T>(fn: () => T, equal: boolean): () => T;
export function getOwner(): unknown;
export function mergeProps(...sources: unknown[]): unknown;
export function createComponent<T>(Comp: (props: T) => JSX.Element, props: T): JSX.Element;
export function untrack<T>(fn: () => T): T;
export const sharedConfig = {};
export const getOwner = null;

(root, effect, memo, getOwner, createComponent, sharedConfig, untrack, mergeProps);
```

## 2. dom-expressions란?

- SolidJS의 렌더링 코어로, JSX 변환 결과를 **DOM에 직접 삽입하는 역할**
- Virtual DOM을 사용하지 않고 **실제 DOM 연산을 효율적으로 수행**
- JSX → 함수 호출로 변환할 때 필요한 `template`, `insert`, `spread` 등을 모두 제공
- LynJS가 원하는 방향(플랫폼 가까운 렌더링)과 완벽히 일치

---

## 3. 왜 dom-expressions를 그대로 쓰지 않고 @lynjs/dom을 만들까?

- LynJS는 Solid와는 다른 런타임 철학을 가짐
  - 예: Shadow DOM 지원, Host/Impl 패턴, Attribute 반영 방식 등
- `dom-expressions`의 코어를 그대로 사용하되,
  - **API entrypoint**를 통합하고
  - **특정 함수만 오버라이드**
  - 향후 LynJS용 확장(HMR, state-preserving host 등)에 대비

## 6. 오버라이드 설계 — insert 함수 예시

- 기존 insert는 DOM에 단순 삽입만 담당
- LynJS에서는 Shadow DOM, hostNode 개념, attribute 반영 등을 통합할 예정
- 오버라이드 예시:

  ```ts
  import { insert as baseInsert } from 'dom-expressions';

  export function insert(parent: Node, value: any, before?: Node) {
    // LynJS 확장 포인트
    if (parent instanceof ShadowRoot) {
      // hostNode 기반 삽입 로직
    }
    return baseInsert(parent, value, before);
  }
  ```

- **핵심 아이디어:** 기존 로직은 유지하되, LynJS가 필요한 훅만 추가

## 7. spread 함수 오버라이드

- LynJS에서는 속성을 단순히 setAttribute로 반영하지 않고,
  - **Custom Element의 속성 반영(attributeChangedCallback)**
  - **@attr 데코레이터 연결**
  - **Style/Property/Listener 처리 분기** 등을 다르게 처리할 수 있음
- 예시:

  ```ts
  import { spread as baseSpread } from 'dom-expressions';

  export function spread(el: Element, props: Record<string, any>, prev?: any) {
    // LynJS용 커스텀 반영 로직
    if (el instanceof HTMLElement && props['data-lyn']) {
      // LynJS 특수 속성 처리
    }
    return baseSpread(el, props, prev);
  }
  ```

# `@lynjs/rxcore`에서 구현해야 할 것들 (업데이트 버전)

## 1) 소유자(Owner)·루트 컨텍스트

### 왜 필요한가?

- `render()`가 `root(dispose => …)`로 수명주기를 연다.
- `effect/memo/cleanup`들이 이 **owner 트리**에 매달려야, 컴포넌트 단위 해제가 가능하다.

### 무엇을 구현하나?

```ts
export type Dispose = () => void;

export function root<T>(fn: (dispose: Dispose) => T, owner?: unknown): T;
export function getOwner(): unknown; // 현재 실행 중 컴퓨테이션의 owner
export function cleanup(fn: () => void): void; // 현재 owner에 정리함수 등록
```

### 실무 포인트

- `dispose()` 호출 시: 등록된 `cleanup` → 컴퓨테이션 의존성 해제 → 자식 owner 정리 순.
- 하이드레이션/이벤트 지연과 엮일 수 있으니 **중복 dispose 안전성** 확보.

---

## 2) 반응 그래프의 핵심: effect / memo / untrack

### 왜 필요한가?

- 런타임 곳곳에서 `effect(prev)` 시그니처를 직접 호출한다. (prev를 다음 실행에 넘겨야 함)
- `memo`는 파생값 캐시로 중복 연산을 줄인다.
- `untrack`은 의존 수집을 끊고 “지금만 읽기”가 필요할 때 쓴다.

### 무엇을 구현하나?

```ts
export function effect<T>(fn: (prev?: T) => T, init?: T): void;
export function memo<T>(fn: () => T, equal?: boolean): () => T;
export function untrack<T>(fn: () => T): T;
```

### 실무 포인트

- 스케줄러는 **마이크로태스크 플러시** 기본. 배치는 추후 옵션화(동기/마이크로태스크/rAF).
- `memo(equal=true)`면 이전 결과와 `Object.is` 비교로 재통지 스킵.

---

## 3) 컴포넌트 실행 헬퍼

### 왜 필요한가?

- JSX 변환물이 `createComponent(Comp, props)`를 호출한다.
- 클래스형/함수형 모두 지원해야 한다.

### 무엇을 구현하나?

```ts
export function createComponent<T>(Comp: (props: T) => any, props: T): any;
```

### 실무 포인트

- 클래스형(`isClassComponent`) 지원이 필요하면 mobx-jsx 예시처럼 감싸주면 되고, 함수형이면 그대로 `Comp(props)`.

---

## 4) props 유틸: mergeProps / splitProps

### 왜 필요한가?

- props 병합 시 **getter 유지(지연 평가)**가 중요하다. 그래야 반응성이 깨지지 않는다.
- split은 구조화된 props 전달 용.

### 무엇을 구현하나?

```ts
export function mergeProps<T extends object>(...sources: T[]): T; // getter 보존 Proxy
export function splitProps<T extends object>(props: T, ...keys: (keyof T)[][]): any[];
```

### 실무 포인트

- `mergeProps`는 단순 스프레드가 아니라 **프로퍼티 디스크립터 보존** 또는 Proxy 기반으로 구현.
- `splitProps`는 mobx-jsx 코드처럼 `Object.getOwnPropertyDescriptors`로 정확히 쪼개기.

---

## 5) 선택자/리스트 헬퍼: createSelector / map

### 왜 필요한가?

- 대규모 리스트에서 **키 단위 갱신**을 구현할 때 selector가 필수.
- `map()`은 입력 배열/시그널 배열 변화에 맞춰 **항목별 디스포저**를 관리한다.

### 무엇을 구현하나?

```ts
export function createSelector<T, U extends T>(source: () => T, equals?: (a: U, b: T) => boolean): (key: U) => boolean;

export function map<T, U>(list: (() => T[]) | T[], mapFn: (v: T, i: number) => U): () => U[];
```

### 실무 포인트

- selector 내부는 **구독자 카운팅**을 하고 `cleanup`으로 감소. 0이 되면 맵에서 제거.
- `map()`은 항목 이동/삭제/삽입을 고려해 **디스포저 배열**을 유지하고, 인덱스 변화를 따라 정리.

## 6) Context API

### 왜 필요한가?

- 상하위로 설정(테마, i18n 등)을 주입/소비.

### 무엇을 구현하나?

```ts
export interface Context {
  id: symbol;
  Provider: (props: { value: unknown; children: any }) => any;
  defaultValue: unknown;
}

export function createContext(defaultValue?: unknown): Context;
export function useContext(ctx: Context): unknown;
```

### 실무 포인트

- provider는 현재 owner의 `context`에 `{[id]: value}`를 얹고 children을 평가.
- `useContext`는 owner 체인을 타고 가장 가까운 값을 조회, 없으면 `defaultValue`.

---

## 7) 코드 스플리팅 헬퍼: lazy

### 왜 필요한가?

- 동적 import와 반응 시스템을 연결해, 로드 후 자동으로 렌더하도록.

### 무엇을 구현하나?

```ts
export function lazy<T extends Function>(fn: () => Promise<{ default: T }>): (props: object) => () => any;
```

### 실무 포인트

- 내부에 `observable.box` 대신 **rxcore 신호**를 쓰면 된다. 로드 완료 시 set, `computed` 대신 `memo`로 값 노출.

## 8) 공유 설정: sharedConfig (하이드레이션/이벤트)

### 왜 필요한가?

- 런타임이 `sharedConfig`를 통해 **하이드레이션 상태/레지스트리/지연 이벤트**를 조정한다.

### 무엇을 구현하나?

```ts
export const sharedConfig: {
  context: { id: string; count: number } | null;
  completed?: Set<Node> | null;
  events?: (Array<[Element, Event]> & { queued?: boolean }) | null;
  registry?: Map<string, Element>;
  load?: (id: string) => any;
  has?: (id: string) => boolean;
  gather?: (root: string) => void;
  done?: boolean;
  getNextContextId(): string;
};
```

### 실무 포인트

- `getHydrationKey()`가 `sharedConfig.getNextContextId()`를 호출한다.
- 하이드레이션 중(`context` truthy & `done` false)에는 **노드 생성 금지 가드**가 걸리므로 런타임과 계약 맞춰야 한다.

## 9) mobx-jsx 예시에서 보이는 추가 시그널

mobx-jsx 샘플은 MobX 위에 rxcore 모양을 **어댑터**로 얹은 것이다. LynJS는 MobX에 의존하지 않으니, 아래 동작을 **자체
시그널/컴퓨테이션**으로 구현하면 된다.

- `autorun` ⇢ `effect`
- `computed` ⇢ `memo`
- `observable.box()` ⇢ `createSignal()`
- `action` ⇢ 배치/스케줄러와 결합(동기 배치 또는 마이크로태스크 큐)

즉, mobx-jsx에서 `box().get()/set()`으로 풀었던 부분은 **rxcore의 getter/setter**로 대체한다.

## 10) 최소 시그니처 요약표 (복붙용)

```ts
// life-cycle / owner
export function root<T>(fn: (dispose: () => void) => T, owner?: unknown): T;
export function getOwner(): unknown;
export function cleanup(fn: () => void): void;

// reactive core
export function effect<T>(fn: (prev?: T) => T, init?: T): void;
export function memo<T>(fn: () => T, equal?: boolean): () => T;
export function untrack<T>(fn: () => T): T;

// component helpers
export function createComponent<T>(Comp: (props: T) => any, props: T): any;
export function mergeProps<T extends object>(...sources: T[]): T;
export function splitProps<T extends object>(props: T, ...keys: (keyof T)[][]): any[];

// selectors & list
export function createSelector<T, U extends T>(source: () => T, equals?: (a: U, b: T) => boolean): (key: U) => boolean;
export function map<T, U>(list: T[] | (() => T[]), mapFn: (v: T, i: number) => U): () => U[];

// context
export interface Context {
  id: symbol;
  Provider: (props: { value: unknown; children: any }) => any;
  defaultValue: unknown;
}
export function createContext(defaultValue?: unknown): Context;
export function useContext(ctx: Context): unknown;

// code splitting
export function lazy<T extends Function>(fn: () => Promise<{ default: T }>): (props: object) => () => any;

// shared config (hydration/events)
export const sharedConfig: {
  context: { id: string; count: number } | null;
  completed?: Set<Node> | null;
  events?: (Array<[Element, Event]> & { queued?: boolean }) | null;
  registry?: Map<string, Element>;
  load?: (id: string) => any;
  has?: (id: string) => boolean;
  gather?: (root: string) => void;
  done?: boolean;
  getNextContextId(): string;
};
```

## 11) 테스트 체크리스트 (Vitest)

- **effect(prev)**: init 전달/반환값이 다음 prev로 들어오는지.
- **의존성 추적**: 읽은 신호만 다시 실행되는지.
- **memo(equal)**: equal=true에서 동일 결과 시 재통지 안 하는지.
- **cleanup/owner**: `root` 종료/`dispose` 호출로 타이머/리스너/컴퓨테이션이 정리되는지.
- **mergeProps**: getter가 보존되어 반응성 유지되는지.
- **createSelector**: 구독자 카운팅과 해제가 정확한지.
- **map**: 삽입/삭제/이동에 따라 디스포저가 누수 없이 관리되는지.
- **sharedConfig**: hydration 플래그 시 노드 생성 가드가 동작하는지.
