# LynJS 요구사항 정의

## 1. 문서 목적

본 문서는 LynJS가 프론트엔드 프레임워크로서 충족해야 하는 기능적 요구사항과 비기능적 요구사항을 정의한다.

`BACKGROUND.md`가 LynJS의 목적과 핵심 가치를 정의한다면, 본 문서는 해당 가치를 실제 구현에서 검증할 수 있는 요구사항으로 구체화한다.

본 문서는 다음 질문에 대한 기준을 제공한다.

- LynJS Component는 어떤 특성을 가져야 하는가?
- 상태와 UI는 어떤 관계를 가져야 하는가?
- Component의 Lifecycle과 Resource는 어떻게 관리되어야 하는가?
- Component 이식성은 어느 수준까지 보장해야 하는가?
- Rendering은 어떤 특성을 가져야 하는가?
- 개발자 경험은 어떤 수준을 목표로 해야 하는가?
- 초기 버전에서 반드시 구현해야 하는 기능은 무엇인가?
- 어떤 기능은 초기 범위에서 제외할 것인가?

구체적인 API, 내부 Runtime 구조, Compiler 구조 및 사용하는 라이브러리는 별도의 설계 문서에서 정의한다.

---

# 2. 요구사항 정의 원칙

LynJS의 요구사항은 구현 방법과 분리한다.

예를 들어 다음은 요구사항이다.

> 상태가 변경되면 해당 상태에 의존하는 UI 영역만 갱신되어야 한다.

반면 다음은 구현 방법이다.

> `dom-expressions`를 사용하여 Fine-grained DOM Binding을 구현한다.

마찬가지로 다음은 요구사항이다.

> Component의 역할과 상태를 간결하고 명확하게 선언할 수 있어야 한다.

다음은 구현 방법이다.

> Decorator를 사용하여 Component Metadata를 선언한다.

본 문서에서는 가능한 한 **LynJS가 무엇을 만족해야 하는가**를 정의하며, **어떻게 구현할 것인가**는 Architecture 및 세부 설계 문서에서 다룬다.

---

# 3. 요구사항 우선순위

요구사항은 다음 세 단계로 구분한다.

| 등급       | 의미                                                |
| ---------- | --------------------------------------------------- |
| **MUST**   | LynJS Core가 반드시 만족해야 하는 요구사항          |
| **SHOULD** | 특별한 기술적 제약이 없다면 만족해야 하는 요구사항  |
| **MAY**    | Core 안정화 이후 선택적으로 제공할 수 있는 요구사항 |

초기 개발에서는 MUST 요구사항을 우선적으로 검증한다.

---

# 4. Component Model 요구사항

## CMP-001 — Component Identity

**MUST**

각 Component Instance는 명확한 Identity를 가져야 한다.

동일한 Component Type에서 여러 Instance가 생성되더라도 각각 독립적인 상태와 Lifecycle을 가져야 한다.

```text
Component Type
    │
    ├── Instance A
    │     └── State A
    │
    └── Instance B
          └── State B
```

한 Instance의 상태 변경이 별도의 공유 상태 선언 없이 다른 Instance의 상태에 영향을 주어서는 안 된다.

---

## CMP-002 — Component Ownership

**MUST**

Component가 소유하는 다음 요소의 Ownership을 명확하게 정의할 수 있어야 한다.

- State
- Effect
- DOM Binding
- Event Subscription
- Resource
- Child Resource

Component가 제거되면 Component가 소유한 Resource를 추적하고 정리할 수 있어야 한다.

---

## CMP-003 — State, Behavior, View 구성

**MUST**

Component는 자신의 상태, 행동 및 UI 표현을 하나의 일관된 Component Model 안에서 구성할 수 있어야 한다.

Component 내부의 상태를 변경하기 위해 Component 외부의 별도 Controller 또는 Store가 반드시 필요해서는 안 된다.

단, Global State 또는 외부 Store 사용을 제한하지 않는다.

---

## CMP-004 — Component Encapsulation

**MUST**

Component는 내부 State와 외부에 공개되는 Interface를 구분할 수 있어야 한다.

외부에서 변경 가능한 값과 Component 내부에서만 사용하는 상태를 명시적으로 구분할 수 있어야 한다.

---

## CMP-005 — Component Composition

**MUST**

Component는 다른 Component를 포함하여 새로운 Component를 구성할 수 있어야 한다.

```text
Application
   │
   └── Component A
          │
          ├── Component B
          └── Component C
```

Component Composition을 위해 별도의 전역 Registry 또는 수동 Mount 작업을 일반적인 사용 과정에서 요구해서는 안 된다.

---

## CMP-006 — Standard Element Identity

**MUST**

LynJS Component는 브라우저에서 실제 Element Identity를 가질 수 있어야 한다.

Component를 Framework 내부의 가상적인 Component Instance로만 표현해서는 안 된다.

---

# 5. State 및 Reactivity 요구사항

## REA-001 — Reactive State

**MUST**

Component는 Reactive State를 정의할 수 있어야 한다.

Reactive State가 변경되면 해당 State를 사용하는 UI 및 Reactive Computation에 변경 사항이 전달되어야 한다.

---

## REA-002 — Automatic Dependency Tracking

**MUST**

일반적인 UI Binding에서 개발자가 State와 UI 사이의 Dependency를 직접 등록하거나 해제할 필요가 없어야 한다.

다음과 같은 수동 Dependency 관리를 기본 사용 방식으로 요구해서는 안 된다.

```text
subscribe(state, element)
unsubscribe(state, element)
```

Framework가 Dependency 관계를 자동으로 관리해야 한다.

---

## REA-003 — Fine-grained Dependency

**MUST**

State Dependency는 가능한 한 실제 State 사용 지점 단위로 추적되어야 한다.

하나의 State 변경으로 인해 해당 State와 관계없는 UI 영역이나 Reactive Computation이 불필요하게 다시 실행되지 않아야 한다.

---

## REA-004 — State Independence

**MUST**

서로 독립적인 State는 독립적으로 갱신될 수 있어야 한다.

예를 들어 `name`과 `count`가 독립적인 State라면,

```text
name ──────▶ Name Binding

count ─────▶ Count Binding
```

`count` 변경이 `Name Binding`의 재계산을 발생시키지 않아야 한다.

---

## REA-005 — Derived State

**SHOULD**

하나 이상의 State로부터 계산되는 Derived State를 정의할 수 있어야 한다.

Derived State는 Dependency가 변경될 경우에만 다시 계산되어야 한다.

---

## REA-006 — Effect

**SHOULD**

State 변경에 따라 UI Rendering 외의 Side Effect를 실행할 수 있는 방법을 제공해야 한다.

Effect의 Dependency 및 Lifecycle은 Framework의 Reactive System과 통합되어야 한다.

---

## REA-007 — Effect Cleanup

**MUST**

Effect가 Resource를 생성할 경우 Cleanup을 정의할 수 있어야 한다.

Component가 해당 Effect를 더 이상 소유하지 않게 되면 Cleanup이 실행되어야 한다.

---

## REA-008 — Batch Update

**SHOULD**

동일한 실행 Context에서 여러 State 변경이 연속적으로 발생할 경우 불필요한 중복 Reactive Computation을 최소화할 수 있어야 한다.

---

## REA-009 — Predictable State Semantics

**MUST**

State의 읽기와 변경 방식은 일관되고 예측 가능해야 한다.

State 종류에 따라 서로 다른 접근 방식을 불필요하게 요구하지 않아야 한다.

---

# 6. Rendering 요구사항

## RND-001 — Declarative UI

**MUST**

UI 구조를 선언적인 방식으로 표현할 수 있어야 한다.

일반적인 Component 개발에서 `document.createElement`, `appendChild`, `textContent` 등의 직접적인 DOM 조작을 요구해서는 안 된다.

직접 DOM API를 사용하는 것은 허용하지만 Framework의 기본적인 UI 작성 방법이 되어서는 안 된다.

---

## RND-002 — Direct Update

**MUST**

State 변경 시 실제 영향을 받는 DOM 영역을 직접 갱신할 수 있어야 한다.

Component 전체 UI Tree의 재생성과 비교를 필수 과정으로 요구해서는 안 된다.

---

## RND-003 — No Virtual DOM Requirement

**MUST**

LynJS Core Rendering Model은 Virtual DOM Tree의 생성과 Diff를 필수 전제로 하지 않아야 한다.

---

## RND-004 — DOM Identity Preservation

**MUST**

State 변경과 관계없는 DOM Node는 가능한 한 기존 Identity를 유지해야 한다.

단순한 Text 또는 Property 변경 때문에 관련 없는 Element가 제거되고 다시 생성되어서는 안 된다.

이는 다음과 같은 브라우저 상태를 안정적으로 유지하기 위해 필요하다.

- Input focus
- Selection
- Scroll state
- Native element state
- DOM reference

---

## RND-005 — Conditional Rendering

**MUST**

State에 따라 UI 영역을 조건부로 생성하거나 제거할 수 있어야 한다.

조건 변경 시 해당 영역의 Lifecycle과 Reactive Resource가 올바르게 관리되어야 한다.

---

## RND-006 — List Rendering

**MUST**

Collection을 기반으로 반복적인 UI를 생성할 수 있어야 한다.

Collection 변경 시 전체 List를 무조건 재생성하지 않고 기존 DOM Identity를 가능한 한 보존할 수 있어야 한다.

---

## RND-007 — Event Binding

**MUST**

선언적인 UI 안에서 DOM Event Handler를 연결할 수 있어야 한다.

Event Handler는 Component의 State와 Behavior에 자연스럽게 접근할 수 있어야 한다.

---

## RND-008 — Dynamic Attribute and Property

**MUST**

State 변경을 DOM Attribute 또는 DOM Property와 연결할 수 있어야 한다.

Property와 Attribute의 차이를 Framework 내부에서 임의로 동일시해서는 안 된다.

---

# 7. Lifecycle 요구사항

## LIF-001 — Connection Lifecycle

**MUST**

Component가 Document에 연결되거나 제거되는 상태를 Framework에서 인식할 수 있어야 한다.

---

## LIF-002 — Lifecycle Ownership

**MUST**

Component가 소유한 Reactive Resource는 Component Lifecycle과 연결할 수 있어야 한다.

```text
Component
   │
   └── Resource Scope
         ├── Effect
         ├── Binding
         └── Subscription
```

---

## LIF-003 — Automatic Cleanup

**MUST**

Component가 영구적으로 사용되지 않게 되었을 때 Framework가 관리하는 Resource가 남아 Memory Leak을 발생시키지 않아야 한다.

---

## LIF-004 — Reconnection

**MUST**

Custom Element는 DOM에서 제거된 후 다시 연결될 수 있으므로 Component의 Reconnection을 지원해야 한다.

단순히 `disconnected` 상태를 Component의 영구적인 파괴로 간주해서는 안 된다.

Connection과 Destruction의 의미를 구분할 수 있어야 한다.

---

## LIF-005 — User-defined Lifecycle

**SHOULD**

개발자가 Component Lifecycle의 특정 시점에 필요한 작업을 정의할 수 있어야 한다.

단, Framework 내부 Lifecycle 관리와 충돌하지 않아야 한다.

---

# 8. Component Interface 요구사항

## INT-001 — Public Property

**MUST**

Component 외부에서 값을 전달하기 위한 Public Property를 정의할 수 있어야 한다.

JavaScript Object, Function 등 Attribute로 표현할 수 없는 값도 전달할 수 있어야 한다.

---

## INT-002 — Attribute

**MUST**

HTML Attribute를 Component Input으로 사용할 수 있어야 한다.

```html
<user-card name="Lyn"></user-card>
```

Attribute와 Property 사이의 관계를 명확하게 정의해야 한다.

---

## INT-003 — Property / Attribute Reflection

**SHOULD**

필요한 경우 Property와 Attribute 사이의 Reflection을 지원할 수 있어야 한다.

Reflection은 명시적인 규칙을 가져야 하며 무조건적인 양방향 동기화를 기본으로 해서는 안 된다.

---

## INT-004 — Event

**MUST**

Component가 외부에 상태 변화나 사용자 Interaction을 알리기 위한 Event를 발생시킬 수 있어야 한다.

Component Event는 표준 DOM Event Model과 호환되어야 한다.

---

## INT-005 — Framework-independent Interface

**MUST**

Component의 Public Interface를 사용하기 위해 소비자가 LynJS의 Reactive Primitive 또는 내부 Runtime API를 알아야 해서는 안 된다.

---

# 9. 웹 표준 및 이식성 요구사항

## WEB-001 — Custom Element Compatibility

**MUST**

LynJS Component는 표준 Custom Element로 사용할 수 있어야 한다.

예를 들어 다음과 같은 사용이 가능해야 한다.

```html
<lyn-counter></lyn-counter>
```

---

## WEB-002 — DOM API Compatibility

**MUST**

LynJS Component는 표준 DOM API를 통해 접근할 수 있어야 한다.

```ts
const counter = document.querySelector('lyn-counter');
```

---

## WEB-003 — DOM Event Compatibility

**MUST**

Component Event는 표준 `EventTarget` 및 DOM Event Propagation Model과 호환되어야 한다.

---

## WEB-004 — Framework-independent Consumption

**MUST**

LynJS Component의 기본적인 사용을 위해 소비 Application 전체가 LynJS로 작성될 필요가 없어야 한다.

---

## WEB-005 — Cross-framework Consumption

**SHOULD**

LynJS Component를 React, Vue, Svelte 또는 Vanilla JavaScript 등의 환경에서 일반적인 Custom Element로 사용할 수 있어야 한다.

Framework별 Adapter 없이 가능한 범위에서는 표준 Custom Element 사용 방식을 우선한다.

---

## WEB-006 — Native Platform Escape Hatch

**MUST**

필요한 경우 개발자가 Framework를 우회하여 표준 DOM API에 접근할 수 있어야 한다.

Framework가 브라우저 기능에 대한 접근을 불필요하게 차단해서는 안 된다.

---

# 10. Developer Experience 요구사항

## DX-001 — Minimal Component Boilerplate

**MUST**

기본 Component를 작성하기 위해 불필요하게 많은 Boilerplate를 요구해서는 안 된다.

State 하나와 Event Handler 하나를 가진 Component는 Framework 내부 개념을 이해하지 않고도 작성할 수 있어야 한다.

---

## DX-002 — Readability

**MUST**

Component 코드를 읽었을 때 다음 사항을 쉽게 식별할 수 있어야 한다.

- Component Input
- Internal State
- Behavior
- UI
- Lifecycle

---

## DX-003 — TypeScript Support

**MUST**

TypeScript를 First-class 개발 환경으로 지원해야 한다.

다음 영역에서 타입 정보를 제공해야 한다.

- Component Property
- State
- Event
- Component API
- JSX

---

## DX-004 — JavaScript Support

**SHOULD**

TypeScript를 사용하지 않는 JavaScript 프로젝트에서도 LynJS를 사용할 수 있어야 한다.

---

## DX-005 — Error Diagnostics

**MUST**

Framework 사용 오류가 발생했을 때 가능한 한 문제의 원인을 식별할 수 있는 오류 메시지를 제공해야 한다.

내부 Runtime Stack만 노출하는 것을 피해야 한다.

---

## DX-006 — Development Server Integration

**MUST**

현대적인 Development Server 및 Build Tool과 통합할 수 있어야 한다.

특정 Build Tool 하나에 Public API가 종속되어서는 안 된다.

---

## DX-007 — HMR

**SHOULD**

개발 중 Component 코드가 변경될 경우 전체 페이지 Reload 없이 변경 사항을 반영할 수 있는 HMR 환경을 제공해야 한다.

State Preservation 여부와 Lifecycle 동작은 별도의 HMR 설계에서 정의한다.

---

## DX-008 — Simple Project Bootstrap

**SHOULD**

새로운 LynJS 프로젝트를 최소한의 단계로 생성하고 실행할 수 있어야 한다.

프로젝트 생성 직후 별도의 복잡한 설정 없이 개발을 시작할 수 있어야 한다.

---

# 11. 성능 요구사항

## PERF-001 — No Unnecessary Component-wide Rendering

**MUST**

하나의 State 변경 때문에 Component 전체 View Function을 반복 실행하는 것을 기본 업데이트 방식으로 사용해서는 안 된다.

---

## PERF-002 — Dependency-local Update

**MUST**

State 변경에 따른 작업량은 가능한 한 해당 State가 영향을 주는 Dependency 범위에 비례해야 한다.

---

## PERF-003 — Stable DOM

**MUST**

변경되지 않은 DOM Node를 불필요하게 교체하지 않아야 한다.

---

## PERF-004 — Resource Cleanup

**MUST**

사용되지 않는 Component 및 Reactive Resource가 Framework 내부 Reference 때문에 Garbage Collection되지 못하는 상황을 최소화해야 한다.

---

## PERF-005 — Runtime Overhead

**SHOULD**

단순한 Component를 사용하기 위해 과도한 Runtime Metadata 또는 Global Runtime State를 생성하지 않아야 한다.

---

## PERF-006 — Performance Measurement

**MUST**

성능에 관한 Architecture 결정은 추측만으로 결정하지 않고 Benchmark 또는 Profiling을 통해 검증할 수 있어야 한다.

Benchmark는 최소한 다음 영역을 포함해야 한다.

- Initial creation
- State update
- List update
- Component creation/destruction
- Memory usage

---

# 12. Accessibility 요구사항

## A11Y-001 — Native Element Semantics

**MUST**

Framework가 브라우저의 기본 HTML Element Semantics를 훼손해서는 안 된다.

---

## A11Y-002 — Standard Attributes

**MUST**

ARIA Attribute 및 Accessibility 관련 표준 Attribute를 사용할 수 있어야 한다.

---

## A11Y-003 — Native Event Behavior

**MUST**

Framework Event System이 Keyboard, Focus 등의 Native Browser Event 동작을 불필요하게 변경해서는 안 된다.

---

# 22. Core Milestone Acceptance Scenario

초기 Core 구현은 최소한 다음 Scenario를 만족해야 한다.

하나의 Counter Component를 정의한다.

```tsx
import { LynElement, element, state } from 'lynjs';

@element('lyn-counter')
class Counter extends LynElement {
  @state()
  count = 0;

  increment() {
    this.count++;
  }

  render() {
    return <button onClick={() => this.increment()}>Count: {this.count}</button>;
  }
}
```

그리고 HTML에서 사용할 수 있어야 한다.

```html
<lyn-counter></lyn-counter>
```

이 Scenario에서 다음 사항을 검증한다.

### Component Identity

`<lyn-counter>` 두 개를 생성하면 각각 독립적인 `count`를 가진다.

### Reactive Update

`count`가 변경되면 `Count: {this.count}`와 연결된 DOM만 갱신된다.

### DOM Identity

`count` 변경 때문에 `button` Element 자체가 불필요하게 교체되지 않는다.

### Event

Click Event가 Component Behavior를 실행할 수 있다.

### Lifecycle

Component를 DOM에서 제거했을 때 Framework가 소유한 Reactive Resource를 적절하게 관리한다.

다시 DOM에 연결했을 때 Component가 정의된 Lifecycle 정책에 따라 정상적으로 동작한다.

### Web Component

다음 표준 DOM API가 정상적으로 동작한다.

```ts
const counter = document.querySelector('lyn-counter');

counter instanceof HTMLElement;
```

### Framework Boundary

Component를 사용하는 측에서는 내부 Reactive Runtime이나 Rendering Infrastructure를 직접 사용할 필요가 없다.

이 Scenario가 성공하는 것을 첫 번째 Core Architecture 검증 기준으로 한다.

# 24. 현재 구현 방향과의 관계

현재 검토된 구현 방향은 다음과 같다.

```text
Requirement
    │
    ▼
Design
    │
    ▼
Implementation
```

예를 들어:

```text
Component 이식성
    ↓
Web-standard Component Boundary
    ↓
Custom Elements
```

```text
명확한 Component Programming Model
    ↓
Object-oriented Component Model
    ↓
LynElement + Decorator
```

```text
선언적인 UI
    ↓
Declarative View Syntax
    ↓
JSX
```

```text
효율적인 UI 업데이트
    ↓
Fine-grained DOM Binding
    ↓
dom-expressions
```

따라서 현재 고려 중인 다음 기술들은 요구사항이 아니라 구현 선택이다.

- Custom Elements
- Class
- Decorator
- JSX
- `dom-expressions`
- TypeScript
- Vite

단, Custom Elements는 Component 이식성 및 웹 표준이라는 핵심 요구사항과 강하게 연결되어 있으므로 현재 Architecture의 기본 전제로 취급한다.

구현 선택을 변경할 경우 해당 변경이 상위 요구사항을 계속 만족하는지를 먼저 검토한다.

---

# 25. 요구사항 변경 원칙

Framework 개발 과정에서 새로운 구현 제약이나 기술적 문제가 발견될 수 있다.

이 경우 구현 편의를 위해 요구사항을 즉시 변경하지 않는다.

다음 순서로 검토한다.

```text
Problem
   ↓
Implementation Alternative
   ↓
Architecture Alternative
   ↓
Requirement Impact
```

먼저 다른 구현 방법으로 기존 요구사항을 만족할 수 있는지 검토한다.

불가능하거나 비용이 지나치게 높은 경우 요구사항 자체의 필요성과 우선순위를 재검토한다.

MUST 요구사항을 변경하는 경우 변경 이유와 영향을 Architecture Decision Record에 기록한다.

---

# 26. 요구사항 추적

향후 Architecture와 구현에서는 주요 기능을 본 문서의 Requirement ID와 연결한다.

예를 들어 Reactivity 설계 문서는 다음과 같이 참조할 수 있다.

```text
Reactivity Architecture

Related Requirements:
- REA-001
- REA-002
- REA-003
- REA-004
- REA-007
- PERF-001
- PERF-002
```

Component Model 문서는 다음 요구사항을 참조한다.

```text
Component Architecture

Related Requirements:
- CMP-001
- CMP-002
- CMP-003
- CMP-004
- LIF-001
- LIF-002
- WEB-001
```

이 방식으로 다음 관계를 유지한다.

```text
Background
    ↓
Requirements
    ↓
Architecture
    ↓
ADR
    ↓
Implementation
    ↓
Tests
```

이를 통해 구현 세부사항이 변경되더라도 해당 구현이 어떤 프로젝트 요구사항을 만족하기 위해 존재하는지 추적할 수 있도록 한다.

# 27. 요구사항 완료 기준

LynJS의 Core Requirement는 단순히 API가 존재한다는 이유만으로 완료된 것으로 판단하지 않는다.

각 MUST Requirement는 다음 조건을 충족해야 한다.

1. 요구사항을 만족하는 구현이 존재한다.
2. 정상 동작을 검증하는 자동화된 테스트가 존재한다.
3. 관련 Edge Case가 정의되어 있다.
4. Public 기능인 경우 사용 방법이 문서화되어 있다.
5. 성능 관련 요구사항인 경우 필요한 Benchmark가 존재한다.
6. 웹 표준 관련 요구사항인 경우 실제 Browser 환경에서 검증된다.

따라서 요구사항의 상태는 다음과 같이 관리할 수 있다.

```text
Proposed
   ↓
Designed
   ↓
Implemented
   ↓
Tested
   ↓
Documented
   ↓
Stable
```

Core Release 대상 MUST Requirement는 최소한 `Tested` 상태에 도달해야 한다.

Public API와 직접 관련된 Requirement는 Release 전에 `Documented` 상태에 도달해야 한다.

# 28. 요약

LynJS의 요구사항은 네 가지 중심 목표에서 출발한다.

### 명확한 Component Model

Component의 State, Behavior, Lifecycle 및 Resource Ownership을 예측할 수 있어야 한다.

### 효율적인 UI 업데이트

State 변경은 실제 영향을 받는 UI 영역에만 전달되어야 한다.

### 웹 표준 기반 이식성

Component의 외부 경계는 가능한 한 웹 플랫폼과 호환되어야 한다.

### 높은 개발자 경험

Framework 내부의 복잡성을 Application 개발자에게 불필요하게 노출하지 않아야 한다.

이 요구사항을 구현하기 위해 현재 Custom Elements, Decorator, JSX, Fine-grained Reactivity 및 `dom-expressions` 등의 기술을 활용할 수 있다.

그러나 이러한 구현 기술은 요구사항보다 하위에 위치한다.

프로젝트의 기술적 의사결정은 항상 다음 순서를 따른다.

```text
Core Values
     ↓
Requirements
     ↓
Design Principles
     ↓
Architecture
     ↓
Implementation
```

LynJS의 구현 방식은 변경될 수 있지만, 해당 구현이 충족해야 하는 요구사항과 프로젝트의 핵심 가치는 명확하게 유지한다.
