# LynJS 설계 원칙

## 1. 문서 목적

본 문서는 LynJS의 설계 및 기술적 의사결정에서 일관되게 적용해야 하는 원칙을 정의한다.

`BACKGROUND.md`가 LynJS가 해결하려는 문제와 핵심 가치를 정의하고, `REQUIREMENTS.md`가 LynJS가 만족해야 할 구체적인 요구사항을 정의한다면, 본 문서는 그 요구사항을 만족시키기 위해 **어떤 방향으로 시스템을 설계할 것인지**에 대한 판단 기준을 제공한다.

본 문서에서는 특정 라이브러리, Decorator API, Compiler 구현 등의 구체적인 기술을 설계 원칙 자체로 정의하지 않는다.

구현 방법은 변경될 수 있지만, 본 문서에서 정의하는 설계 원칙은 LynJS의 Programming Model이 유지되는 한 가능한 한 안정적으로 유지되어야 한다.

---

# 2. 설계 원칙의 우선순위

모든 설계 목표를 동시에 완벽하게 만족시키는 것은 불가능할 수 있다.

서로 다른 요구사항이 충돌할 경우 LynJS는 다음 순서를 기본적인 판단 기준으로 사용한다.

```text
Correctness
    ↓
Predictability
    ↓
Interoperability
    ↓
Developer Experience
    ↓
Performance
    ↓
Implementation Simplicity
```

단, 이 순서는 성능이나 구현 단순성이 중요하지 않다는 의미가 아니다.

예를 들어 성능 최적화를 위해 Component Lifecycle을 예측하기 어려운 구조로 변경해서는 안 되며, 구현이 간단하다는 이유로 Public API의 일관성을 희생해서도 안 된다는 의미다.

반대로 동일한 Programming Model과 동작을 제공할 수 있다면 더 단순하고 효율적인 구현을 우선한다.

---

# 3. Programming Model과 구현을 분리한다

LynJS에서 가장 중요한 설계 원칙 중 하나는 **사용자가 경험하는 Programming Model과 Framework 내부 구현을 분리하는 것**이다.

사용자가 LynJS를 사용할 때 이해해야 하는 개념과 Framework 내부에서 필요한 개념은 동일할 필요가 없다.

예를 들어 내부 Runtime에는 다음과 같은 요소가 존재할 수 있다.

```text
Dependency Graph
Reactive Node
Subscriber
DOM Binding
Scheduler
Scope
Metadata
Compiler Transform
```

하지만 일반적인 Component를 작성하기 위해 사용자가 이 모든 개념을 직접 이해해야 해서는 안 된다.

사용자가 이해해야 하는 모델은 가능한 한 다음 수준에 머물러야 한다.

```text
Component
 ├─ Input
 ├─ State
 ├─ Behavior
 ├─ Lifecycle
 └─ View
```

따라서 설계 시 다음 질문을 항상 확인한다.

> 내부 구현의 복잡성이 Public Programming Model로 유출되고 있지 않은가?

Framework 내부에서 필요한 추상화와 Application 개발자에게 필요한 추상화를 구분한다.

---

# 4. Component는 명확한 Identity와 Ownership을 가진다

LynJS에서 Component는 명확한 Identity를 가진 독립적인 UI 단위다.

각 Component Instance는 자신의 상태와 Resource를 소유한다.

```text
Component Instance
       │
       ├─ State
       ├─ Behavior
       ├─ Reactive Resources
       ├─ Event Resources
       └─ View
```

Component가 소유하는 Resource의 범위가 명확해야 하며, 소유권이 불명확한 암묵적인 전역 Resource를 가능한 한 만들지 않는다.

이 원칙은 다음과 같은 문제를 예방하기 위한 것이다.

- Effect Cleanup 누락
- Event Subscription 누수
- Component 간 State 오염
- 불명확한 Lifecycle
- Memory Leak
- 제거된 Component를 참조하는 Reactive Resource

Component와 관련된 Resource는 가능한 한 명확한 Owner를 가져야 한다.

---

# 5. Lifecycle은 Ownership에서 파생된다

Lifecycle은 별도의 Callback 집합이 아니라 **Component가 Resource를 소유하기 때문에 발생하는 결과**로 다룬다.

Component가 활성화되면 해당 Component가 필요로 하는 Resource를 사용할 수 있고, Component가 더 이상 Resource를 소유하지 않으면 정리할 수 있어야 한다.

```text
Component
    │
    ▼
Ownership Scope
    │
    ├─ Reactive Binding
    ├─ Effect
    ├─ Event Subscription
    └─ Resource
```

Lifecycle 설계에서는 다음을 명확히 구분한다.

```text
Constructed
Connected
Disconnected
Destroyed / Disposed
```

특히 웹 플랫폼에서는 DOM에서 제거된 Element가 다시 연결될 수 있으므로 `disconnected`와 영구적인 `destroyed` 상태를 동일하게 취급하지 않는다.

Lifecycle Hook 자체의 개수보다 **Resource가 언제 유효하고 언제 정리되는가**를 명확하게 만드는 것을 우선한다.

---

# 6. 상태는 사용되는 위치 가까이에 둔다

Component 내부에서만 사용되는 State는 가능한 한 해당 Component가 소유한다.

상태가 필요 이상으로 넓은 Scope에 위치하면 Ownership과 변경 영향을 추적하기 어려워진다.

따라서 기본 원칙은 다음과 같다.

> **State should live as close as possible to where it is owned and used.**

Component 내부 State를 단순히 공유할 가능성이 있다는 이유만으로 Global State로 승격시키지 않는다.

State Scope는 실제 요구사항에 따라 확장한다.

```text
Local State
    ↓ 필요할 경우
Parent-owned State
    ↓ 필요할 경우
Shared State
    ↓ 필요할 경우
Application State
```

이 원칙은 특정 State Management API를 강제하기 위한 것이 아니라 State Ownership을 명확하게 유지하기 위한 것이다.

---

# 7. 상태와 외부 입력을 구분한다

Component가 내부적으로 소유하는 State와 외부에서 전달되는 Input은 개념적으로 구분한다.

```text
Outside
   │
   ▼
Input / Property
   │
   ▼
Component
   │
   ├─ Internal State
   └─ Behavior
```

외부 Input을 내부 상태처럼 임의로 변경하거나 내부 State를 무분별하게 외부에 노출하지 않는다.

Public Interface와 Internal State의 경계를 명확하게 유지한다.

이를 통해 Component의 데이터 흐름을 추론하기 쉽게 만든다.

---

# 8. 상태 변경의 영향을 국소화한다

LynJS는 State가 변경되었을 때 변경의 영향을 가능한 한 정확한 범위로 제한한다.

핵심 원칙은 다음과 같다.

> **Update what changed, and nothing more.**

예를 들어 다음 세 개의 상태가 존재한다면,

```text
name
age
theme
```

각 상태에 의존하는 UI가 독립적일 경우 Dependency 역시 독립적으로 유지되는 것을 지향한다.

```text
name  ─────▶ Name UI

age   ─────▶ Age UI

theme ─────▶ Theme UI
```

`age` 변경 때문에 `name`이나 `theme`과 관련된 UI를 다시 계산하지 않는다.

이 원칙은 단순한 성능 최적화 이상의 의미를 가진다.

State 변경의 영향 범위가 명확할수록 Runtime 동작 역시 더 쉽게 예측할 수 있다.

---

# 9. DOM Identity를 보존한다

DOM은 단순한 Rendering 결과물이 아니다.

DOM Element에는 브라우저가 관리하는 실제 상태가 존재할 수 있다.

예를 들어 다음과 같다.

- Focus
- Selection
- Scroll position
- Form state
- Media state
- Custom Element state
- DOM reference
- Browser-specific native state

따라서 State 변경과 무관한 DOM Node를 불필요하게 제거하거나 다시 생성하지 않는다.

```text
Before

Component
 ├─ Input
 ├─ Button
 └─ Result


State Change
       │
       ▼

Only Result changes


After

Component
 ├─ Input   ← same node
 ├─ Button  ← same node
 └─ Result  ← updated
```

Fine-grained Update의 목적은 단순히 DOM Mutation 횟수를 줄이는 것이 아니라 **실제 UI 객체의 Identity를 안정적으로 유지하는 것**에도 있다.

---

# 10. 선언성과 직접 갱신은 동시에 유지한다

사용자는 UI가 어떻게 변경되어야 하는지를 명령형으로 직접 기술하지 않아야 한다.

즉 다음 두 목표를 동시에 만족해야 한다.

```text
Application
    │
    ▼
Declarative UI

Runtime
    │
    ▼
Precise DOM Mutation
```

사용자는 UI의 최종적인 관계를 선언하고, Framework가 State Dependency와 실제 DOM 변경을 처리한다.

효율성을 이유로 Application 코드에 저수준 DOM Mutation을 반복적으로 요구하지 않는다.

반대로 선언성을 제공한다는 이유만으로 변경되지 않은 UI 전체를 반복 처리할 필요도 없다.

---

# 11. 웹 플랫폼을 우선한다

LynJS는 브라우저가 이미 해결하고 있는 문제를 Framework 내부에서 불필요하게 다시 구현하지 않는다.

가능한 경우 다음 Web Platform 기능을 그대로 활용한다.

```text
DOM
Custom Elements
EventTarget
Events
Properties
Attributes
ES Modules
CSS
Shadow DOM
Form APIs
Browser Lifecycle
```

새로운 Framework Abstraction을 추가하기 전에 다음 질문을 확인한다.

1. 웹 플랫폼에 이미 해결책이 존재하는가?
2. 기존 API를 그대로 사용하면 어떤 문제가 발생하는가?
3. 새로운 추상화가 실제로 개발 복잡성을 낮추는가?
4. 새로운 추상화 때문에 상호 운용성이 감소하지 않는가?

Framework API를 추가하는 것은 기본 선택이 아니라 필요성이 있을 때 선택하는 방향을 따른다.

---

# 12. 표준은 경계에서 가장 중요하다

LynJS는 모든 내부 구현을 Web API만으로 작성해야 한다는 원칙을 두지 않는다.

중요한 것은 Framework 외부와 접하는 **Boundary**다.

```text
Other Framework
      │
Vanilla JS
      │
HTML
      │
      ▼
┌─────────────────┐
│ Standard Boundary│
└─────────────────┘
        │
        ▼
      LynJS
        │
        ▼
Internal Runtime
```

내부에서는 Compiler, Reactive Runtime, Metadata, Scheduling 등의 기술을 사용할 수 있다.

그러나 Component 외부 Interface는 가능한 한 다음과 같은 웹 표준과 호환되어야 한다.

- Element
- Property
- Attribute
- Event
- DOM API

이를 다음 원칙으로 정리한다.

> **Standards at the boundary, freedom inside.**

---

# 13. 상호 운용성을 기본값으로 설계한다

Framework 외부 환경과의 상호 운용성을 나중에 Adapter로 해결해야 하는 부가 기능으로 취급하지 않는다.

Public Component Interface를 설계하는 단계부터 다른 환경에서 사용할 수 있는지를 고려한다.

예를 들어 특정 Framework Runtime 객체를 Public Property에 필수적으로 요구하거나, Component Event를 Framework 내부 Event Bus에서만 전달하는 방식은 피한다.

가능한 경우 다음 방향을 우선한다.

```text
Input
  → JavaScript Property / Attribute

Output
  → DOM Event

Identity
  → DOM Element
```

Framework-specific 기능이 필요할 경우 표준 Interface 위에 추가 Layer로 제공하는 것을 우선한다.

---

# 14. Public API는 최소화한다

새로운 API를 추가하는 것은 Framework가 제공하는 기능을 늘리는 동시에 사용자가 학습해야 할 개념을 늘리는 것이다.

따라서 Public API를 쉽게 확장하지 않는다.

새로운 API를 추가하기 전에 다음 기준을 검토한다.

- 기존 API로 자연스럽게 해결할 수 없는가?
- 단순한 Utility로 해결할 수 없는가?
- Web Platform API를 그대로 사용할 수 없는가?
- 반복되는 실제 사용 사례가 존재하는가?
- 새로운 개념의 학습 비용보다 이점이 큰가?
- 장기간 유지할 수 있는 의미를 가지고 있는가?

기능 수보다 개념 수를 관리하는 것을 중요하게 생각한다.

---

# 15. 하나의 개념에는 하나의 기본 경로를 제공한다

동일한 문제를 해결하는 여러 API를 동시에 제공하면 선택의 자유는 증가하지만 Framework의 Mental Model은 복잡해진다.

따라서 일반적인 작업에는 하나의 명확한 기본 경로를 제공한다.

예를 들어 State를 선언하는 방식이 있다면 일반 Component State를 위한 권장 방식은 하나여야 한다.

필요한 경우 Escape Hatch를 제공할 수 있지만 기본 Programming Model과 동일한 중요도로 여러 접근법을 제공하지 않는다.

```text
Recommended Path
      │
      ├──────────────▶ 대부분의 경우
      │
      └── Escape Hatch ▶ 특수한 경우
```

---

# 16. 특별한 Framework 문법을 최소화한다

Framework를 사용하기 위해 JavaScript와 HTML의 기본적인 의미를 과도하게 변경하지 않는다.

가능한 경우 기존 언어의 의미를 유지한다.

예를 들어 다음 개념을 Framework 전용 의미로 불필요하게 재정의하지 않는다.

- Class
- Property
- Method
- Event
- DOM Element
- JavaScript expression

LynJS 특유의 문법이나 규칙을 추가해야 할 경우 그 규칙이 해결하는 문제가 충분히 명확해야 한다.

목표는 새로운 언어를 만드는 것이 아니라 **JavaScript와 Web Platform 위에서 더 나은 UI Programming Model을 만드는 것**이다.

---

# 17. 일반적인 코드는 일반적으로 보여야 한다

단순한 Component를 작성하는 코드가 Framework 내부 구조 때문에 복잡해져서는 안 된다.

예를 들어 상태 값을 증가시키는 행위는 가능한 한 JavaScript에서 상태를 변경하는 것처럼 읽혀야 한다.

```ts
this.count++;
```

이를 위해 내부에서는 복잡한 Dependency Tracking이 발생하더라도 사용자 코드에는 필요 이상의 Reactive Plumbing을 노출하지 않는 것을 지향한다.

이 원칙을 다음과 같이 정리한다.

> **Simple things should look simple.**

복잡한 기능은 복잡할 수 있지만, 기본적인 기능까지 복잡하게 보여서는 안 된다.

---

# 18. 명시성과 Boilerplate를 구분한다

LynJS는 Boilerplate를 줄이는 것을 중요하게 생각하지만 모든 명시적인 표현을 제거하는 것을 목표로 하지는 않는다.

다음은 서로 다른 개념이다.

```text
Explicitness
    ≠
Boilerplate
```

Component의 Public Input인지 Internal State인지 구분하는 정보는 의미 있는 명시성일 수 있다.

반면 Framework가 내부적으로 추론할 수 있는 정보를 매번 반복해서 작성하도록 요구한다면 Boilerplate가 될 수 있다.

따라서 API를 단순화할 때는 코드 길이만 보지 않고 **해당 표현이 중요한 의미를 전달하는지**를 기준으로 판단한다.

---

# 19. Magic은 제한하고 관찰 가능하게 만든다

Framework가 자동으로 처리하는 기능은 개발자 경험을 개선할 수 있다.

하지만 자동 동작이 너무 많아지면 Runtime의 행동을 예측하기 어려워질 수 있다.

따라서 자동화는 다음 조건을 만족해야 한다.

- 일관된 규칙을 따른다.
- 코드만 보고 어느 정도 추론할 수 있다.
- Debugging할 수 있다.
- 필요할 경우 동작을 명시적으로 제어할 수 있다.
- 숨겨진 Global State에 과도하게 의존하지 않는다.

자동 Dependency Tracking 자체는 허용하지만 Dependency가 언제 생성되고 해제되는지 설명할 수 있어야 한다.

Compiler Transformation 역시 허용하지만 Source와 Runtime 동작 사이의 관계를 Debugging할 수 있어야 한다.

---

# 20. Side Effect는 Rendering과 구분한다

UI를 계산하거나 Binding을 생성하는 과정과 외부 Side Effect를 가능한 한 개념적으로 구분한다.

Side Effect에는 다음과 같은 작업이 포함될 수 있다.

- Network request
- Timer
- External subscription
- Storage
- Analytics
- DOM 외부 Resource
- Imperative third-party library

Side Effect가 View 표현의 부수적인 결과로 암묵적으로 반복 실행되는 구조를 피한다.

Side Effect는 명확한 Ownership과 Lifecycle을 가져야 한다.

```text
Component
    │
    ├─ View
    │
    └─ Side Effect
          │
          └─ Cleanup
```

이를 통해 UI Update와 외부 Resource 관리의 관계를 명확하게 유지한다.

---

# 21. Escape Hatch를 제공한다

Framework가 모든 사용 사례를 완벽하게 추상화할 수 있다고 가정하지 않는다.

필요한 경우 개발자가 Web Platform에 직접 접근할 수 있어야 한다.

예를 들어 다음과 같은 작업을 Framework가 불필요하게 막아서는 안 된다.

- 직접 DOM API 사용
- Element reference 획득
- Native Event 등록
- Third-party DOM Library 통합
- Browser-specific API 사용

Escape Hatch는 Framework 설계 실패의 표시가 아니라 Platform Framework에서 필요한 기능이다.

다만 일반적인 사용 사례가 모두 Escape Hatch에 의존해야 한다면 Framework API 자체를 재검토해야 한다.

---

# 22. 성능 최적화는 Programming Model을 침범하지 않는다

성능은 LynJS의 중요한 목표지만 성능을 위해 Application API가 지나치게 복잡해지는 것을 피한다.

개발자가 일반적인 Component를 작성하기 위해 다음과 같은 내부 최적화 개념을 직접 관리하지 않아야 한다.

```text
Dependency Node
DOM Patch
Scheduler Queue
Template Cache
Binding Index
```

필요한 Optimization은 가능한 한 Runtime이나 Compile-time에서 처리한다.

Application 개발자가 성능을 위해 특별한 API를 사용해야 하는 경우에는 다음 조건을 만족해야 한다.

- 실제로 비용이 큰 사용 사례다.
- 자동 Optimization이 어렵다.
- 기본 동작도 Correctness를 유지한다.
- Optimization API가 선택적이다.

---

# 23. 성능은 측정한다

성능에 관한 설계 결정은 직관이나 Framework 간 이미지에 의존하지 않는다.

성능 문제는 Benchmark와 Profiling을 통해 확인한다.

특히 다음 두 가지를 구분한다.

```text
Architectural Efficiency

vs.

Micro Optimization
```

LynJS는 우선적으로 불필요한 작업을 발생시키지 않는 Architecture를 선택한다.

그 이후 실제 측정을 통해 Hot Path를 최적화한다.

다음과 같은 요소를 지속적으로 측정할 수 있어야 한다.

- Initial Rendering
- Reactive Update
- List Operations
- Component Creation
- Component Disposal
- Memory
- Bundle Size
- Runtime Overhead

Benchmark 결과를 Framework의 마케팅 목표가 아니라 Regression을 방지하기 위한 Engineering Tool로 활용한다.

---

# 24. Compile-time과 Runtime의 역할을 구분한다

LynJS는 모든 문제를 Runtime에서 해결해야 한다거나 모든 문제를 Compiler에서 해결해야 한다는 원칙을 갖지 않는다.

문제의 성격에 따라 적절한 위치에서 처리한다.

정적으로 판단할 수 있는 정보는 Compile-time에서 처리할 수 있다.

```text
Static Structure
Known Binding
Metadata
Syntax Transformation
```

실행 시점에만 결정되는 정보는 Runtime이 처리한다.

```text
State
Lifecycle
Dynamic Dependency
Runtime Resource
```

기준은 기술적 순수성이 아니라 다음과 같다.

- Runtime 비용
- Debuggability
- Build Complexity
- DX
- Portability
- 유지보수성

Compile-time과 Runtime은 경쟁 관계가 아니라 서로 다른 문제를 해결하는 계층으로 본다.

---

# 25. 외부 의존성은 Infrastructure로 취급한다

LynJS는 모든 기능을 직접 구현하는 것을 목표로 하지 않는다.

검증된 외부 기술이 프로젝트 요구사항을 충분히 만족한다면 이를 활용할 수 있다.

다만 외부 라이브러리를 사용하는 경우 해당 기술이 LynJS의 Programming Model 자체가 되지 않도록 책임 경계를 유지한다.

```text
Application
     │
     ▼
LynJS Programming Model
     │
     ▼
LynJS Architecture
     │
     ▼
External Infrastructure
```

외부 의존성을 선택할 때는 다음을 평가한다.

- 요구사항 충족 여부
- 프로젝트 유지 가능성
- API 안정성
- 라이선스
- Bundle 영향
- Performance
- 교체 가능성
- LynJS Public API로의 Leakage 여부

현재 선택한 기술이 존재한다는 이유만으로 Architecture 전체를 해당 기술의 내부 모델에 맞추지 않는다.

---

# 26. 구현 기술은 교체 가능성을 고려한다

모든 내부 기술을 언제든 완전히 교체할 수 있도록 만드는 것은 현실적인 목표가 아니다.

그러나 구현 기술의 세부사항이 Public API 전체에 퍼지는 것은 피한다.

특히 다음 경계를 중요하게 관리한다.

```text
Public API
    │
Component Model
    │
Reactive Model
    │
Rendering Infrastructure
    │
Build Infrastructure
```

하위 계층의 기술 선택이 변경될 때 상위 계층을 불필요하게 변경하지 않도록 책임을 분리한다.

예를 들어 특정 Rendering Infrastructure를 사용하더라도 해당 라이브러리의 Helper API가 Application 코드 전반에 노출되는 구조를 피한다.

---

# 27. Progressive Complexity를 지향한다

LynJS는 처음 사용하는 개발자가 Framework 전체 구조를 이해한 뒤에야 Component를 작성할 수 있는 모델을 지향하지 않는다.

기본적인 사용은 적은 개념만으로 가능해야 한다.

```text
Level 1
Component + State + View

        ↓

Level 2
Properties + Events + Lifecycle

        ↓

Level 3
Effects + Derived State + Composition

        ↓

Level 4
Advanced Integration / Optimization
```

사용자가 필요에 따라 더 깊은 개념을 학습할 수 있도록 한다.

고급 기능 때문에 기본 사용 경험을 복잡하게 만들지 않는다.

---

# 28. Convention은 강제보다 우선한다

Framework가 모든 구조를 Runtime 제약으로 강제할 필요는 없다.

잘못된 사용이 Correctness나 Framework Architecture를 깨뜨리는 경우에는 제약이 필요하지만, 단순한 코드 스타일이나 구조적 선호는 Convention으로 제공하는 것을 우선한다.

다음 세 가지를 구분한다.

```text
Invariant
    → 반드시 강제

Recommended Pattern
    → 문서와 Tooling으로 유도

Style Preference
    → Framework Core에서 강제하지 않음
```

이를 통해 Framework Runtime이 불필요한 규칙 집합으로 커지는 것을 방지한다.

---

# 29. 오류는 가능한 한 빠르고 가까이에서 발견한다

Framework 사용 오류는 가능한 한 실제 원인에 가까운 위치에서 발견되어야 한다.

잘못된 Component 정의나 API 사용이 있다면 이후 Rendering 과정에서 모호한 오류를 발생시키기보다 가능한 한 빠르게 알려주는 것을 지향한다.

Development 환경에서는 다음 정보를 제공할 수 있어야 한다.

- 어떤 Component에서 발생했는가
- 어떤 Property 또는 Binding과 관련되어 있는가
- 어떤 Framework 규칙을 위반했는가
- 수정 가능한 경우 어떤 방향으로 수정해야 하는가

Production 환경에서는 불필요한 Diagnostic Cost를 제거할 수 있도록 한다.

---

# 30. Type System은 API를 설명해야 한다

TypeScript는 단순히 오류를 줄이는 도구가 아니라 LynJS Programming Model을 설명하는 수단으로 활용한다.

Public API의 Type은 Framework 개념을 자연스럽게 표현해야 한다.

타입 시스템 때문에 API가 지나치게 복잡해지거나 Runtime 동작과 Type 동작이 크게 달라지는 것을 피한다.

다음 원칙을 따른다.

> **Types should describe the runtime model, not invent another one.**

복잡한 Generic Trick을 사용하는 것보다 사용자가 이해할 수 있는 Type을 우선한다.

---

# 31. 기본 Web Behavior를 존중한다

LynJS는 Native Element와 Browser의 기본 동작을 가능한 한 보존한다.

특히 다음 영역을 불필요하게 변경하지 않는다.

- Focus
- Keyboard interaction
- Form behavior
- Event propagation
- Accessibility semantics
- CSS cascade
- DOM ownership

Framework 편의를 위해 Native Behavior를 변경해야 할 경우 명확한 이유가 있어야 한다.

이는 Accessibility와 다른 Web Library와의 상호 운용성에도 직접적인 영향을 준다.

---

# 32. Styling을 Core Programming Model에 강제하지 않는다

LynJS Component는 특정 Styling Solution에 종속되지 않아야 한다.

기본적으로 표준 CSS를 사용할 수 있어야 하며, 필요에 따라 다음 방식을 선택할 수 있는 구조를 지향한다.

- Global CSS
- Shadow DOM
- CSS Modules
- CSS-in-JS
- 외부 Styling Library

Framework가 하나의 Styling 기술을 사용하는 것을 요구하지 않는다.

Component Encapsulation 요구에 따라 LynJS가 Helper를 제공할 수 있지만 Styling 방식 자체를 Framework Identity로 만들지 않는다.

---

# 33. 기능을 추가하기 전에 조합 가능성을 확인한다

새로운 Framework Feature를 추가하기 전에 기존 Primitive의 조합으로 해결할 수 있는지 확인한다.

예를 들어 특정 상태 패턴을 지원하기 위해 새로운 Component 종류를 추가하기보다 기존 State, Event, Composition으로 자연스럽게 해결할 수 있다면 기존 Primitive를 활용한다.

```text
Few Powerful Primitives
        │
        ▼
    Composition
        │
        ▼
Complex Features
```

많은 특수 API보다 적은 수의 일관된 Primitive를 선호한다.

---

# 34. Core와 Ecosystem을 구분한다

모든 프론트엔드 문제를 LynJS Core가 직접 해결하지 않는다.

다음과 같은 영역은 Core와 독립적인 확장 기능이 될 수 있다.

- Router
- Global State
- Data Fetching
- Animation
- Form Library
- SSR Integration
- DevTools
- Testing Utilities

Core에 기능을 추가하는 기준은 해당 기능이 LynJS Component Programming Model을 구성하는 필수 요소인지 여부다.

Core가 지나치게 커지면 Framework의 학습 비용과 유지보수 비용이 함께 증가한다.

---

# 35. SSR을 위해 Client Model을 왜곡하지 않는다

SSR은 중요한 확장 영역이지만 Client-side Component Model을 SSR 구현 편의를 위해 지나치게 제한하지 않는다.

대신 Client Component Model에서 서버에서도 표현 가능한 부분과 Browser에서만 가능한 부분의 경계를 명확하게 만든다.

```text
Component Model
      │
      ├─ Platform-independent
      │
      └─ Browser-specific
```

SSR은 Core Architecture가 안정된 이후 해당 경계를 활용하여 확장한다.

초기 단계에서는 SSR 구현 자체보다 **향후 SSR을 구조적으로 불가능하게 만드는 결정**을 피하는 것을 우선한다.

---

# 36. HMR은 Lifecycle을 우회해서는 안 된다

HMR은 개발자 경험을 위한 기능이지만 Framework의 기본 Lifecycle 규칙을 깨뜨리는 별도의 Component Model을 만들어서는 안 된다.

HMR이 State Preservation이나 Instance 교체를 수행하더라도 일반 Runtime과 최대한 동일한 Ownership 및 Cleanup 규칙을 유지해야 한다.

개발 환경만을 위한 특수 동작은 Production Programming Model에 영향을 주지 않아야 한다.

---

# 37. 최적화보다 Correctness가 먼저다

Fine-grained Reactivity와 직접 DOM Update는 최적화된 Runtime을 만들 수 있지만, 성능을 위해 잘못된 상태나 오래된 UI를 허용해서는 안 된다.

Optimization을 적용할 때는 다음 순서를 따른다.

```text
Correctness
    ↓
Clear Semantics
    ↓
Measurement
    ↓
Optimization
```

Optimization 때문에 사용자에게 예측하기 어려운 특별 규칙을 추가해야 한다면 비용과 효과를 다시 검토한다.

---

# 38. 설계 결정은 기록한다

중요한 Architecture Decision은 코드에만 남기지 않는다.

다음과 같은 결정은 ADR(Architecture Decision Record)로 관리한다.

- 특정 Component 기반 선택
- Rendering Infrastructure 선택
- Reactivity Model 선택
- Decorator 도입
- Property / Attribute 정책
- Shadow DOM 정책
- SSR Architecture
- HMR Architecture
- Package Boundary

ADR은 최소한 다음 내용을 포함한다.

```text
Context
Decision
Alternatives
Rationale
Consequences
Status
```

기술 선택이 변경될 경우 기존 ADR을 삭제하기보다 변경 이유를 추적할 수 있도록 새로운 결정을 기록한다.

---

# 39. 설계 원칙과 현재 구현 방향

현재 고려하는 구현 방향은 본 문서의 원칙을 다음과 같이 실현한다.

| 설계 목표                  | 현재 구현 방향              |
| -------------------------- | --------------------------- |
| 웹 표준 Component Boundary | Custom Elements             |
| 명확한 Component Ownership | `LynElement` 기반 객체 모델 |
| 간결한 Component 선언      | Decorator                   |
| 선언적 View                | JSX                         |
| 변경 범위 최소화           | Fine-grained Reactivity     |
| Fine-grained DOM Rendering | `dom-expressions`           |
| Type-safe DX               | TypeScript                  |
| 현대적인 개발 환경         | Vite 기반 Tooling           |

위 항목들은 현재의 구현 선택이며 설계 원칙 자체는 아니다.

예를 들어 Decorator보다 더 명확하고 간결한 Component 선언 방법이 존재하고 프로젝트 요구사항을 더 잘 만족한다면 해당 기술은 변경될 수 있다.

`dom-expressions` 역시 LynJS의 Fine-grained Update 요구사항을 구현하기 위해 현재 선택한 Rendering Infrastructure다.

구현 기술의 변경 여부는 해당 기술이 본 문서의 설계 원칙과 상위 요구사항을 얼마나 잘 만족하는지를 기준으로 판단한다.

---

# 40. 설계 검토 체크리스트

새로운 API, Runtime 기능 또는 Architecture 변경을 제안할 때 다음 질문을 검토한다.

### Component Model

- Component Ownership이 명확한가?
- Lifecycle을 예측할 수 있는가?
- State와 Input의 경계가 명확한가?

### Web Platform

- 브라우저가 이미 제공하는 기능을 불필요하게 재구현하고 있지 않은가?
- Component 외부 Interface는 표준적인가?
- 다른 환경과 상호 운용할 수 있는가?

### Reactivity

- 변경 영향을 필요한 범위로 제한하는가?
- 불필요한 Reactive Computation을 만들지 않는가?
- Resource Cleanup이 명확한가?

### Developer Experience

- 새로운 개념을 추가할 필요가 있는가?
- 단순한 사용 사례가 단순하게 보이는가?
- Framework 내부 구조가 Application API에 노출되지 않는가?
- 오류를 이해하고 Debugging할 수 있는가?

### Architecture

- Public API와 구현 세부사항이 적절히 분리되어 있는가?
- 특정 외부 기술의 내부 모델이 Framework 전체로 유출되고 있지 않은가?
- 기존 Primitive를 조합하여 해결할 수 없는가?

### Performance

- 실제로 성능 문제가 확인되었는가?
- Optimization이 Correctness나 DX를 훼손하지 않는가?
- 측정 가능한가?

새로운 기능은 위 기준을 모두 완벽히 만족할 필요는 없지만, 어떤 Trade-off를 선택했는지 설명할 수 있어야 한다.

---

# 41. Anti-Patterns

LynJS 설계에서는 다음 방향을 피한다.

## Framework-specific abstraction first

웹 플랫폼에 이미 충분한 모델이 있는데도 Framework 전용 API부터 만드는 것.

## Hidden ownership

State, Effect 또는 Subscription을 누가 소유하고 언제 정리하는지 알기 어려운 구조.

## Global implicit behavior

Component의 동작이 숨겨진 Global State나 등록 순서에 과도하게 의존하는 구조.

## Full component work for local changes

작은 State 변경 때문에 관련 없는 Component View 전체를 반복 처리하는 구조.

## Infrastructure leakage

Rendering Library 또는 Compiler 내부 Helper가 Application API에 직접 노출되는 구조.

## API proliferation

기존 Primitive의 조합으로 해결할 수 있는 문제마다 새로운 API를 추가하는 것.

## Optimization-driven API

Runtime 최적화를 위해 일반적인 Application 코드에 내부 최적화 개념을 강제하는 것.

## Standard purity over usability

형식적인 표준 사용 자체를 위해 실제 개발 경험을 불필요하게 악화시키는 것.

## DX over interoperability

짧은 코드만을 위해 Component의 표준 Boundary와 상호 운용성을 포기하는 것.

---

# 42. 원칙 간 충돌 처리

설계 원칙은 실제 문제에서 서로 충돌할 수 있다.

예를 들어 다음과 같은 상황이 발생할 수 있다.

### 표준성 vs 개발자 경험

Web API를 그대로 사용하는 것이 지나치게 반복적이라면 Framework 추상화를 제공할 수 있다.

단, Component의 외부 Boundary는 가능한 한 표준 형태를 유지한다.

### 성능 vs 단순성

실제 성능 문제가 확인되었고 자동 최적화가 어렵다면 선택적인 Advanced API를 제공할 수 있다.

기본 API를 복잡하게 만들지는 않는다.

### 자동화 vs 예측 가능성

자동화를 통해 Boilerplate를 크게 줄일 수 있다면 허용한다.

단, 자동 동작은 일관되고 Debugging 가능해야 한다.

### 외부 의존성 vs 자체 구현

검증된 외부 기술이 요구사항을 충분히 만족한다면 재사용을 우선한다.

다만 Public API가 외부 기술에 종속되거나 핵심 Architecture를 제한한다면 자체 Adapter 또는 구현을 검토한다.

Trade-off가 중요한 경우 ADR로 결정과 근거를 기록한다.

# 43. 설계 원칙 요약

LynJS의 설계 방향은 다음 구조로 요약할 수 있다.

```text
                    LynJS

                 Core Values
                     │
                     ▼
                Requirements
                     │
                     ▼
             Design Principles
                     │
        ┌────────────┼────────────┐
        │            │            │
   Predictable   Platform     Efficient
    Ownership    Friendly      Updates
        │            │            │
        ├────────────┼────────────┤
        │            │            │
     Simple      Standard      Stable
       DX        Boundary       Identity
        │            │            │
        └────────────┼────────────┘
                     │
                     ▼
              Architecture
                     │
                     ▼
          Implementation Choices
```

LynJS는 Component의 Ownership과 Lifecycle을 명확하게 유지한다.

상태 변경의 영향을 가능한 한 국소화한다.

DOM Identity와 브라우저의 기본 동작을 존중한다.

웹 플랫폼이 제공하는 기능을 우선 활용한다.

Component 외부 Boundary는 가능한 한 표준 형태를 유지한다.

내부 Runtime의 복잡성을 Application 개발자에게 노출하지 않는다.

적은 수의 일관된 Primitive를 조합하여 기능을 확장한다.

성능은 추측이 아니라 측정을 기반으로 최적화한다.

외부 기술은 목적이 아니라 Infrastructure로 활용한다.

그리고 구현 기술보다 Programming Model과 프로젝트의 핵심 가치를 우선한다.

---

# 44. 최종 원칙

LynJS의 설계 결정을 가장 압축해서 표현하면 다음과 같다.

> **웹이 이미 해결한 것은 웹에 맡긴다.**

> **Component가 소유한 것은 Component의 Lifecycle 안에서 관리한다.**

> **변경되지 않은 것은 다시 처리하지 않는다.**

> **내부가 복잡해져도 사용자 모델은 단순하게 유지한다.**

> **Component의 외부 경계는 가능한 한 표준으로 유지한다.**

> **새로운 추상화보다 기존 Primitive의 조합을 먼저 고려한다.**

> **성능을 위해 예측 가능성을 희생하지 않는다.**

> **구현 기술은 교체될 수 있지만 Programming Model은 안정적으로 유지한다.**

이 원칙들을 LynJS의 Architecture, API, Runtime, Tooling 및 Ecosystem 설계의 공통 판단 기준으로 사용한다.
